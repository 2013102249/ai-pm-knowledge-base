# 第 1 章｜W1 职业认知 · 技术通识 · 提示词与上下文工程

> 结论前置：W1 不教写代码，只交付三样可验收的东西——岗位认知坐标系、够用的技术判断力、能直接进作品集的当堂产出。本章面向 UI 设计、软件测试、运营等跨行业转岗学员，全程以「一线城市 AI 产品经理就业」为结果导向，技术深度以「能判断可行性」为界。它承接开营，向 W2 的模型边界、微调、评测与合规定调，并为 W3–W6 的主项目实战统一术语与工作方法。凡大纲未覆盖的转岗工具，本章一律以【补充】标注后补入，讲次主题与编号一字不改。

## 0.1 本章学习目标

1. 说出 AI PM 四类岗位（平台型 / 应用型 / 模型型 / 数据型）的职责边界，并画出与传统 PM 的差异表。
2. 写出一份【补充】个人能力迁移表，标明自己的可迁移能力、缺口与本周补法。
3. 用产品经理语言解释 Token、概率式生成、上下文窗口、幻觉、训练与推理的区别、参数量与能力的关系，并判断 5 个常见技术说法的正误。
4. 套用「角色 / 任务 / 约束 / 示例 / 输出格式 / 验收标准」模板写出一条可复用提示词，并判定它属于提示词工程还是上下文工程。
5. 用「产品拆解六层」拆解一个 Chat 类与一个 RAG / Agent 类产品，输出对照表。
6. 当堂产出个人定位画布、行业选择矩阵与 8 周学习契约，就业目标写到可验收程度。

## 0.4 本章核心概念

| 概念 | 一句话定义 | 易混淆点 |
| --- | --- | --- |
| AI 产品经理（AI PM） | 对「用大模型解决用户问题并可持续交付」负责的人 | 不等于算法工程师，也不等于只会写提示词 |
| 大模型 | 按概率预测下一个 Token 的大规模神经网络 | 不是「数据库」，回答是生成不是检索 |
| Token | 模型读写文本的最小计费与计算单位 | 不等于一个汉字或一个单词 |
| 上下文窗口 | 单次请求里模型能「看见」的信息总量上限 | 不等于长期记忆，超出即被截断 |
| 提示词 | 本次请求中给模型的指令文本 | 只是上下文的一部分，不是全部 |
| 上下文工程 | 决定模型该看到哪些信息、以何种顺序与结构看到 | 不是「把话说漂亮」的话术 |
| RAG | 先检索外部知识再让模型作答的架构 | 不是微调，不改模型参数 |
| Agent | 能自主规划、调用工具、多步完成目标的系统 | 不是聊天机器人，失败代价更高 |
| PRD | 描述需求、方案、异常与验收的产品文档 | AI 产品 PRD 必须写模型不确定性兜底 |
| 评测集 | 一组带标准答案或评分规则的用例 | 不是随便试几条提示词 |
| 北极星指标 | 最能代表产品长期价值的唯一核心指标 | 不等于日活，也不等于调用量 |
| MVP | 最小可验证、能收到真实反馈的产品版本 | 不是「半成品」，必须闭环 |

## 0.5 本章关键方法框架

**框架一：产品拆解六层（W1D4 主用）。** 结论前置：任何 AI 产品都能拆成六层，缺一层就说明拆解没做完。

| 步骤 | 层 | 要回答的问题 |
| --- | --- | --- |
| 1 | 用户 | 谁在用，付费者与使用者是否同一人 |
| 2 | 场景 | 在什么触发条件下用，频次多高 |
| 3 | 输入 | 用户给什么，系统额外喂什么 |
| 4 | 处理 | 模型、检索、工具、护栏如何串起来 |
| 5 | 输出 | 交付什么形态，错了怎么兜底 |
| 6 | 度量 | 用什么指标判断这次交付是好的 |

可复用模板：逐层填一句结论，六句连起来即一页产品拆解卡。

**框架二：可复用提示词六要素（W1D3 主用）。**

```
【角色】你是……
【任务】把……做成……
【约束】不得…… / 必须…… / 只用……
【示例】输入示例 → 输出示例
【输出格式】表格 / JSON / 分点，字段为……
【验收标准】满足……才算合格，否则重做
```

结论前置：缺「验收标准」的提示词无法规模化复用，这是学员最常见的漏项。

**框架三：【补充】行业选择矩阵与个人定位画布（W1D5 主用）。** 步骤：① 列 3 个候选赛道；② 对每个赛道按「岗位密度 × 迁移成本」打高 / 中 / 低（评分为教学假设，须按当周招聘信息自行校准）；③ 选「密度高且迁移成本低」者为首选；④ 用定位画布填「我是谁 / 我能迁移什么 / 我缺什么 / 我补什么 / 我的证据物 / 我的目标岗位」；⑤ 输出 8 周学习契约一页纸。

## 0.6 本章典型项目案例

结论前置：开源项目的价值不在跑通代码，而在读懂它做过的产品决策。

- **[R02 dair-ai/Prompt-Engineering-Guide](https://github.com/dair-ai/Prompt-Engineering-Guide)**：场景是提示词技巧散落各处、新人无从下手；决策是把内容沉淀为「入门指南 + 进阶技巧 + 论文与 Notebook」三层结构；结果是不同基础的读者都能找到入口。可借鉴的产品决策：知识类 / 工具类产品必须分层交付，降低跨行业学员的进入门槛。
- **[R01 microsoft/generative-ai-for-beginners](https://github.com/microsoft/generative-ai-for-beginners)**：场景是零基础转岗者需要技术通识；决策是 21 课配套视频、作业与多语言；结果是「看 + 做 + 验」闭环。可借鉴的产品决策：面向转岗人群，产品要提供可验收作业，而不是只给阅读 material。
- **[R15 langgenius/dify](https://github.com/langgenius/dify)**（跨章少量复用）：场景是模型输出不稳定、难以直接上生产；决策是把模型能力封装成可视化编排的 Agent 与工作流；结果是把不确定性关进可控流程。可借鉴的产品决策：AI 产品的核心决策往往是「用流程约束模型」，而非「换更强的模型」。

## 0.9 本章常见问题（FAQ）

1. **Q：不会写代码能不能做 AI PM？** 能。AI PM 的门槛是「能判断技术可行性 + 能定义验收标准」，不是能实现模型；推导公式交给算法。
2. **Q：提示词写得好就等于上下文工程吗？** 不等于。提示词是上下文的一个子集，上下文工程还要决定检索什么、截断什么、按什么顺序喂。
3. **Q：模型越新、参数越大，产品就一定越好吗？** 不一定。够用原则下，成本、延迟、确定性往往比参数量更决定产品能否上线。
4. **Q：幻觉能不能彻底消除？** 不能彻底消除，只能靠检索、护栏、兜底与人工确认把风险压到场景可接受。
5. **Q：跨行业转岗是不是要从零开始？** 不是。UI 设计的用户视角、测试的验收思维、运营的度量意识都是可直接迁移的资产。
6. **Q：RAG 和微调该选哪个？** 需要外部 / 更新知识时用 RAG，需要固化风格与格式时再考虑微调；W2 展开。
7. **Q：Chat、Copilot、Agent 怎么一眼分清？** 看谁掌握主动权：用户主导是 Chat，人主机辅是 Copilot，机主人审是 Agent。
8. **Q：一线城市就业，本周最先该准备什么？** 先定岗位类型与赛道，再让每讲产出成为作品集素材，而不是先囤课。
9. **Q：示例里的数字能写进简历吗？** 不能。本章所有假设性数字均为教学假设，简历只写个人真实项目与可核验结果。

## W1D1 周一 · 开营 + AI 产品经理岗位全景

### 学习目标

1. 说出平台型、应用型、模型型、数据型四类 AI PM 的职责边界与核心交付物。
2. 画出 AI PM 与传统 PM 的差异表，并标出自己最可能的入口岗位。
3. 写出【补充】个人能力迁移表与 8 周学习契约，就业目标落到一线城市可投岗位。

### 核心概念

结论前置：AI PM 是「对用大模型解决用户问题并可持续交付负责的人」，不是「会写提示词的人」。岗位类型的划分依据是「你交付什么、对什么指标负责」，不是公司大小。

| 岗位类型 | 核心交付物 | 对什么负责 | 转岗友好入口 |
| --- | --- | --- | --- |
| 平台型 | 模型 / 能力平台、编排工具 | 稳定性、成本、复用率 | 有工程或测试背景者 |
| 应用型 | 面向用户的 AI 功能或产品 | 用户价值、留存、转化 | UI 设计、运营背景者 |
| 模型型 | 模型选型、评测、微调方案 | 效果指标、边界定义 | 需补技术判断力 |
| 数据型 | 数据、知识库、评测集 | 数据质量、覆盖度 | 软件测试背景者 |

与传统 PM 的差异（结论前置：差异集中在「不确定性」和「验收方式」）：

| 维度 | 传统 PM | AI PM |
| --- | --- | --- |
| 需求确定性 | 输入到输出基本可预期 | 同输入可能不同输出 |
| 验收方式 | 功能通过即验收 | 需用评测集与评分规则验收 |
| 异常兜底 | 报错页即可 | 必须写幻觉、越权、拒答兜底 |
| 成本结构 | 主要是研发人力 | 每次调用都有 Token 成本 |
| 核心协作 | 设计、研发、测试 | 增加算法 / 评测 / 合规角色 |

### 方法框架

## W1D2 周二 · 大模型原理通识（产品经理版）

### 学习目标

1. 用产品经理语言说出 Token、概率式生成、上下文窗口、幻觉、训练与推理的区别、参数量与能力的关系。
2. 判断 5 个常见技术说法的正误并给出正解。
3. 说出「PM 不需要会推导公式，但必须能判断技术可行性」的含义，并用清单判断一个需求是否可行。

### 核心概念

结论前置：大模型是「按概率预测下一个 Token 的机器」；PM 只需理解它如何影响产品行为，不需要理解它内部怎么算。六个概念一张卡：

| 概念 | 产品经理版解释 | 对产品的影响 |
| --- | --- | --- |
| Token | 模型读写文本的最小单位，按它计费 | 决定成本与延迟，长文要省着用 |
| 概率式生成 | 逐 Token 采样，同问可能不同答 | 不能按「固定输出」写验收 |
| 上下文窗口 | 单次请求能看见的信息上限 | 超出会被截断，信息要排优先级 |
| 幻觉 | 一本正经编出错误内容 | 必须写兜底与人工确认 |
| 训练 vs 推理 | 训练是「读书」，推理是「答题」 | 改知识通常靠检索，不是靠训练 |
| 参数量与能力 | 参数越大一般能力越强，但非正比保证 | 够用即可，别为参数迷信买单 |

一句话记住边界：模型擅长「模式化的语言与归纳」，不擅长「精确事实、实时数据、严格计算」。

### 方法框架

**技术可行性判断清单（5 问，逐条给是 / 否）**：① 需求是否依赖精确事实或实时数据？② 输出是否要求 100% 一致？③ 上下文是否可能超出窗口？④ 错了是否有兜底路径？⑤ 每次调用的 Token 成本是否可接受？五问全「否」或可兜底，才判为可行；任一为「是」且无解，就退回改方案。

**5 个常见误解与正解（结论前置：误解都源于把模型当成人或当成数据库）**：

| # | 常见误解 | 正解 |
| --- | --- | --- |
| 1 | 「模型像人一样理解问题」 | 它按概率续写，不理解不等于答不对，但随时可能跑偏 |
| 2 | 「问两次答案该一样」 | 概率式生成，默认就是不保证一致 |
| 3 | 「模型知道最新消息」 | 训练数据有截止点，实时信息要靠检索 |
| 4 | 「参数越大产品越好」 | 成本、延迟、确定性常比参数更关键 |
| 5 | 「幻觉是 bug，修好就没了」 | 是生成机制的特性，只能压风险不能根除 |

结论前置：PM 不需要会推导公式，但必须能判断技术可行性——判断的依据就是上面 5 问，不是数学。

### 案例拆解

**[R01 microsoft/generative-ai-for-beginners](https://github.com/microsoft/generative-ai-for-beginners)**：场景是转岗者被术语吓住；决策是用 21 课把概念配图、配作业讲清；结果是零基础也能建立通识。可迁移点：给非技术干系人讲模型，要用类比 + 影响，而不是结构图。

**[R03 wangxuqi/Prompt-Engineering-Guide-Chinese](https://github.com/wangxuqi/Prompt-Engineering-Guide-Chinese)**：场景是英文术语形成门槛；决策是做中文译本并补 AIGC 章节；结果是概念可快速对照。可迁移点：跨行业团队更需要「术语对照表」这类低成本共识工具。

### 课堂讲解要点

结论前置：本讲只讲「模型行为对产品的影响」，不讲网络结构；

| 环节 | 内容 | 板书 |
| --- | --- | --- |
| 导入 | 用一次「同问不同答」演示 | 概率式生成 |
| 讲授 | 六概念卡 + 5 误解 | 六格表 |
| 演示 | 用 5 问清单判一个需求 | 清单打勾 |
| 练习 | 小组判需求可行性 | 结论 + 依据 |
| 总结 | 「不需推公式」定调 | 一句话类比 |

生活类比：大模型像「只背过海量题库、没真懂知识的学生」——大多数题答得漂亮，偶尔会一本正经地编一个不存在的答案，所以得给它配个错题本（评测集）和监考（兜底）。常见误区：一上来讲参数与网络层，把设计 / 测试背景学员直接劝退；正确顺序是「行为 → 影响 → 可行性」。

### 练习与讨论题

- 个人练习 1：用六概念卡向「完全不懂技术的家人」解释幻觉。参考要点：不出现公式，用 1 个生活例子，讲清「为什么要兜底」。
- 个人练习 2：对「用大模型做实时订单状态查询」跑 5 问清单并下结论。参考要点：命中「依赖实时数据」且需检索 / 兜底，结论应为「需改方案」。
- 小组研讨：参数量更大的模型一定更适合我们的产品吗。评分 rubric：给出明确否 / 条件判断 2 分、引用成本 / 延迟 / 确定性 2 分、举出 1 个场景 1 分。

### 常见问题

1. **Q：要不要会算 Token 成本？** 要会估算量级，不用会精算；知道「长上下文更贵、每次调用都计费」就够做方案取舍。
2. **Q：概率式生成是不是就没法做产品？** 不是。用评测集定验收、用护栏与兜底控风险，正是 AI PM 的核心工作。
3. **Q：训练与推理分不清会出事吗？** 会。把「补知识」误当成「要训练」，会误判工期与成本；正确方向通常是 RAG。

### 本讲术语

| 术语 | 英文 / 缩写 | 释义 | 易混点 |
| --- | --- | --- | --- |
| Token | Token | 文本最小计算与计费单位 | 不等于字数 |
| 概率式生成 | Probabilistic Generation | 逐 Token 采样输出 | 不等于随机乱码 |
| 上下文窗口 | Context Window | 单次可见信息上限 | 不等于长期记忆 |
| 幻觉 | Hallucination | 编造合理但错误的内容 | 不等于普通答错 |
| 推理 | Inference | 训练后用模型算输出 | 与训练相对 |

- **[R01 microsoft/generative-ai-for-beginners](https://github.com/microsoft/generative-ai-for-beginners)**：看基础概念课，解决「六概念怎么讲给非技术人」。
- **[R03 wangxuqi/Prompt-Engineering-Guide-Chinese](https://github.com/wangxuqi/Prompt-Engineering-Guide-Chinese)**：看术语与入门章节，解决「英文概念对照」。
- **[R27 openai/openai-cookbook](https://github.com/openai/openai-cookbook)**：看基础 API 示例，解决「一次调用到底发生了什么」的直觉。

懂原理像看天气预报：不必会算气压公式，但要知道「今天可能下雨」，才记得给产品带把伞。

## W1D3 周三 · 提示词工程与上下文工程

### 学习目标

1. 说出提示词工程与上下文工程的区别及演进关系。
2. 套用六要素模板写出一条带验收标准的可复用提示词。
3. 用上下文预算与信息优先级表解释「为什么上下文工程是产品能力而非话术」。

### 核心概念

结论前置：提示词工程是「把一句话说清楚」，上下文工程是「决定模型这次该看到哪些信息」；前者是技巧，后者是产品能力。演进关系：单点提示词 → 结构化提示词 → 带检索 / 记忆 / 工具的上下文系统，复杂度升级，但目标始终是「让模型在有限窗口内看到最该看的东西」。

| 维度 | 提示词工程 | 上下文工程 |
| --- | --- | --- |
| 关注对象 | 一条指令的措辞 | 整个信息供给链路 |
| 典型手段 | 角色、Few-shot、格式约束 | 检索、切片、排序、截断、记忆、工具 |
| 失败表现 | 输出跑偏、格式乱 | 信息缺失、被截断、答非所问 |
| 归属 | 个人技巧 | 产品与架构决策 |
| 可复用性 | 靠复制粘贴 | 靠模板与管线 |

### 方法框架

**可复用提示词六要素模板**（结论前置：缺「验收标准」不算可复用）：

```
【角色】你是资深 AI 产品面试官
【任务】针对我给出的项目描述，出 3 道追问
【约束】只问决策依据，不问概念背诵；不得虚构我的项目数据
【示例】输入「我做了知识库问答」→ 输出「为什么选 RAG 而不是微调？」
【输出格式】编号列表，每题一行，不超过 40 字
【验收标准】3 题均可回答、且都指向可核验决策，否则重出
```

**上下文预算与信息优先级表**（预算以「窗口有限」为前提，占比为教学假设，按场景调整）：

| 优先级 | 信息类型 | 处理方式 | 预算占比（教学假设） |
| --- | --- | --- | --- |
| 1 | 任务指令与验收标准 | 必留，放首尾 | 20% |
| 2 | 与本次问题最相关的检索片段 | 按相关度排序后放入 | 50% |
| 3 | 少量示例（Few-shot） | 只留 1–2 条最典型 | 15% |
| 4 | 历史对话摘要 | 压缩成要点，不整段塞 | 10% |
| 5 | 冗余背景 | 超预算先截断 | 5% |

**为什么上下文工程是产品能力而非话术（三条论证）**：① 它决定「给模型看什么」，直接定义产品能不能答对，属于需求定义；② 它要在有限窗口里做取舍，是成本 / 延迟 / 质量的权衡，属于方案设计；③ 它需要检索、切片、排序等工程配合，能被写进 PRD 和验收标准，属于可交付物。话术改一句话，工程改一条链路——这就是分界线。

### 案例拆解

**[R02 dair-ai/Prompt-Engineering-Guide](https://github.com/dair-ai/Prompt-Engineering-Guide)**：场景是「怎么写提示词」缺系统方法；决策是按基础到进阶把技巧分层沉淀；结果是可照着练。可迁移点：把个人经验产品化为「分层模板」，正是六要素模板的来源。

**[R04 Meirtz/Awesome-Context-Engineering](https://github.com/Meirtz/Awesome-Context-Engineering)**：场景是提示词技巧在生产系统里不够用；决策是用综述把检索、记忆、工具等上下文组件组织起来；结果是形成生产级方法论。可迁移点：从「话术」升级到「链路」，是 AI PM 能力升级的分水岭。

### 课堂讲解要点

结论前置：本讲用「同一需求、两种写法」的现场对比让学员看见差距；

| 环节 | 内容 | 板书 |
| --- | --- | --- |
| 导入 | 现场对比烂提示词与好提示词 | 六要素 |
| 讲授 | 两者区别 + 演进 | 对比表 5 行 |
| 演示 | 填上下文预算表 | 优先级排序 |
| 练习 | 各写一条带验收标准的提示词 | 模板卡 |
| 总结 | 「产品能力而非话术」定调 | 一句话类比 |

生活类比：提示词像「点菜时说的一句『少放辣』」，上下文工程像「给厨师备好食材、菜谱、忌口清单和上菜顺序」——只喊一句少放辣，厨房照样可能端错菜。常见误区：疯狂收藏「万能提示词」，却不设计信息供给；收藏的是话术，缺的是链路。

### 练习与讨论题

- 个人练习 1：把一句「帮我写个总结」改写成六要素齐全的提示词。参考要点：六要素无缺，验收标准可判断。
- 个人练习 2：给一个长文档问答场景填上下文预算表，说明先截断哪类信息。参考要点：优先砍冗余背景，保留指令与高相关片段。
- 小组研讨：为什么说上下文工程能写进 PRD，而提示词话术不能。评分 rubric：给出「可验收 / 可权衡 / 需工程配合」中 ≥2 条 3 分、结论前置 1 分。

### 常见问题

1. **Q：提示词工程过时了吗？** 没有。它是上下文工程的基础功，只是不再等于全部；先写好一条，再谈组织一条链路。
2. **Q：上下文窗口够大是不是就不用取舍？** 仍要取舍。信息越多越易「淹没重点」，且成本与延迟随长度上升。
3. **Q：Few-shot 示例是不是越多越好？** 不是。示例占预算，1–2 条最典型的通常足够，多了反而挤掉检索内容。

### 本讲术语

| 术语 | 英文 / 缩写 | 释义 | 易混点 |
| --- | --- | --- | --- |
| 提示词 | Prompt | 本次请求的指令文本 | 只是上下文一部分 |
| 上下文工程 | Context Engineering | 组织模型可见信息的工程能力 | 不是话术 |
| Few-shot | Few-shot | 给少量示例引导输出 | 不等于微调 |
| 上下文预算 | Context Budget | 窗口内各信息的分配 | 不等于字数上限 |
| 信息优先级 | Information Priority | 决定谁先被看、谁先被砍 | 不等于相关度排序本身 |

### 参考资料

- **[R02 dair-ai/Prompt-Engineering-Guide](https://github.com/dair-ai/Prompt-Engineering-Guide)**：看基础提示与进阶技巧章节，解决「六要素怎么落笔」。
- **[R04 Meirtz/Awesome-Context-Engineering](https://github.com/Meirtz/Awesome-Context-Engineering)**：看综述导读与实现指南目录，解决「从提示词到上下文系统」的演进。
- **[R03 wangxuqi/Prompt-Engineering-Guide-Chinese](https://github.com/wangxuqi/Prompt-Engineering-Guide-Chinese)**：看中文入门章节，解决「术语对照与课堂共读」。

### 本讲收尾

做上下文像收拾出差行李箱：不是把整个家塞进去，而是按行程挑出最该带的几件，箱子才扣得上、路才走得动。

## W1D4 周四 · AI 产品形态拆解

### 学习目标

1. 用分类框架对比 Chat / Copilot / Agent / 嵌入式 AI / AI 原生应用五类形态。
2. 用「产品拆解六层」拆解一个 Chat 类与一个 RAG / Agent 类产品，输出对照表。
3. 说出形态选择如何影响确定性要求与成本结构。

### 核心概念

结论前置：分类看三件事——交互范式、确定性要求、成本结构；主动权在谁手里，决定产品该怎么写兜底。lobe-chat 类对话前端产品在本节仅作 Chat 形态的定性举例，不作编号引用。

| 形态 | 交互范式 | 价值主张 | 确定性要求 | 成本结构 |
| --- | --- | --- | --- | --- |
| Chat | 用户主导、一问一答 | 低门槛获取答案 | 中，答错可追问 | 单次调用为主 |
| Copilot | 人主机辅、嵌入现有流程 | 提效、不打断习惯 | 高，错会污染主流程 | 高频调用，需控延迟 |
| Agent | 机主人审、多步自主 | 替人完成整段任务 | 最高，须可回滚可审计 | 多轮 + 工具调用，成本最高 |
| 嵌入式 AI | 无感、藏在原功能里 | 老功能悄悄变聪明 | 高但可降级 | 调用分散，按量计费 |
| AI 原生应用 | 无 AI 即不成立 | 全新体验与工作流 | 因场景而异 | 以模型为核心成本项 |

一句话判断：主动权越交给模型，确定性要求与成本就越高，兜底越要写厚。

### 方法框架

**产品拆解六层示范**（结论前置：把两个产品放同一张表，差异一眼可见）：

| 六层 | Chat 类（lobe-chat 类，定性举例） | RAG / Agent 类（[R15 langgenius/dify](https://github.com/langgenius/dify) 与 [R19 infiniflow/ragflow](https://github.com/infiniflow/ragflow)，跨章少量复用） |
| --- | --- | --- |
| 用户 | 通用问答者，付费者常即使用者 | 企业知识管理员 / 业务操作员 |
| 场景 | 临时提问、探索式查询 | 从固定知识库取据、按流程办事 |
| 输入 | 一句话 + 少量历史对话 | 文档 / 问题 + 检索片段 + 工作流配置 |
| 处理 | 直接请求模型生成 | 先解析切片召回，再编排生成与工具调用 |
| 输出 | 一段文本，答错靠追问 | 带出处的答案或流程结果，可审计可回滚 |
| 度量 | 满意度、追问率 | 召回命中率、答案有据率、任务完成率 |

结论前置：Chat 的复杂度在「体验」，RAG / Agent 的复杂度在「信息供给与流程约束」；这正是 D3 上下文工程的落地形态。

### 案例拆解

**[R15 langgenius/dify](https://github.com/langgenius/dify)**：场景是模型输出不稳、难直接上生产；决策是把模型能力封装成可视化编排的 Agent 与工作流；结果是把不确定性关进可控流程。可迁移点：Agent 形态的产品价值不在「更聪明」，而在「可回滚、可审计」。

**[R19 infiniflow/ragflow](https://github.com/infiniflow/ragflow)**：场景是知识散落在文档里、直接问模型会编；决策是先把文档解析、切片、召回评测做扎实；结果是答案有据可查。可迁移点：RAG 产品的第一决策是「信息怎么进上下文」，不是「用哪个模型」。

### 课堂讲解要点

结论前置：本讲用「同一需求做成五种形态」让学员看见成本与兜底的差异；

| 环节 | 内容 | 板书 |
| --- | --- | --- |
| 导入 | 现场给一个需求，问「做成哪种」 | 五形态 |
| 讲授 | 五形态对比表 | 四列对比 |
| 演示 | 六层拆解两个产品 | 六层对照表 |
| 练习 | 小组拆解一款常见 AI 功能 | 六层卡 |
| 总结 | 「主动权 = 成本」定调 | 一句话类比 |

生活类比：Chat 像「问路窗口」，Copilot 像「副驾提醒」，Agent 像「代驾把你送到家」，嵌入式 AI 像「藏在洗衣机里的水位感应」，AI 原生应用像「为自驾重新设计的车」——越往后，越要给它装刹车和保险。常见误区：把所有带对话框的产品都叫 Chat，忽略 Copilot 与 Agent 的兜底责任差异。

### 练习与讨论题

- 个人练习 1：把「会议纪要整理」分别设计成 Copilot 与 Agent 版，写出兜底差异。参考要点：Agent 版须写可回滚、可审计、失败重试。
- 个人练习 2：用六层拆解一款你常用的 AI 功能并填卡。参考要点：六层无遗漏，度量层须给具体指标名。
- 小组研讨：为什么 Agent 的成本结构高于 Chat。评分 rubric：答出多轮 + 工具调用 + 兜底审计 ≥2 项 3 分、结论前置 1 分。

### 常见问题

1. **Q：lobe-chat 类产品和 Agent 怎么分？** 看主动权：前者用户一步步问，后者系统自己规划多步；本节仅把前者作 Chat 形态的定性举例。
2. **Q：嵌入式 AI 算不算「真 AI 产品」？** 算。它的产品难点恰是「无感且可降级」，对确定性要求反而更高。
3. **Q：形态选错会怎样？** 会用错兜底与预算：把 Agent 当 Chat 做，上线后必在成本与错责上翻车。

### 本讲术语

| 术语 | 英文 / 缩写 | 释义 | 易混点 |
| --- | --- | --- | --- |
| Chat | Chat | 用户主导的一问一答形态 | 不等于所有对话框产品 |
| Copilot | Copilot | 嵌入流程、人主机辅 | 与 Agent 的主动权不同 |
| Agent | Agent | 自主规划并调用工具的多步系统 | 不等于聊天机器人 |
| 嵌入式 AI | Embedded AI | 藏在原功能里的无感智能 | 不等于独立 App |
| RAG | RAG | 先检索再生成的架构 | 不等于微调 |

### 参考资料

- **[R05 liyupi/ai-guide](https://github.com/liyupi/ai-guide)**：看 Prompt / RAG / Agent 索引，解决「中文语境下形态怎么归类」。
- **[R15 langgenius/dify](https://github.com/langgenius/dify)**：看可视化编排与工作流（跨章复用），解决「Agent 形态怎么拆」。
- **[R19 infiniflow/ragflow](https://github.com/infiniflow/ragflow)**：看文档解析、切片与召回（跨章复用），解决「RAG 形态怎么拆」。

### 本讲收尾

选形态像选交通工具：去楼下买盐骑共享单车就够，跨城办事才需要订车票配保险，选重了贵、选轻了到不了。

## W1D5 周五 · 行业选择 + 职业规划工作坊

### 学习目标

1. 填出行业选择矩阵（赛道 × 岗位密度 × 迁移成本），并选出首选赛道。
2. 完成个人定位画布，写清可迁移能力与证据物。
3. 走完 8 周职业规划工作坊流程，当堂产出一页纸职业规划。

### 核心概念

结论前置：选赛道看「岗位密度 × 迁移成本」，不看热度；你的最优解是「从当前位置最顺、到达最稳」的那条路，不是最热闹的那条。

| 候选赛道 | 岗位密度 | 迁移成本 | 适配原岗位 | 建议 |
| --- | --- | --- | --- | --- |
| 企业知识库 / 办公提效 | 高 | 低 | 测试、运营 | 首选，重 RAG 与验收 |
| AI 内容 / 营销工具 | 中 | 低 | 运营、UI 设计 | 次选，重体验与度量 |
| 智能客服 / 对话应用 | 中 | 中 | 测试、运营 | 可进，重兜底与评测 |
| 模型平台 / 开发工具 | 中 | 高 | 有工程背景者 | 慎选，先补技术判断力 |

表中高 / 中 / 低为教学假设评分，须按当周一线城市招聘信息自行校准；本节不引用任何未校验的企业经营数据。

### 方法框架

**行业选择矩阵三步**：① 列 3 个候选赛道；② 逐项打「岗位密度 / 迁移成本」高 / 中 / 低；③ 选「密度高、迁移成本低」为首选，其余作备选。

**【补充】个人定位画布（六格）**：我是谁（原岗位 + 年限）｜我能迁移什么（≥3 条）｜我缺什么（≥2 条）｜我补什么（对应 W1–W8 讲次）｜我的证据物（每讲产出）｜我的目标岗位（一线城市 / 应用型 AI PM）。

**8 周职业规划工作坊流程（当堂产出）**：① 自评能力雷达 6 项；② 填行业选择矩阵；③ 填定位画布；④ 把 8 周每周产出映射到证据物；⑤ 小组互评并定稿一页纸；⑥ 讲师收契约。当堂产出＝一页纸职业规划，含目标岗位、首选赛道、8 周证据物清单、每周验收标准。

### 案例拆解

**[R38 1c7/chinese-independent-developer](https://github.com/1c7/chinese-independent-developer)**：场景是学员选题凭感觉；决策是用真实项目列表按形态归类观察；结果是能看出哪类场景供给多、哪类少。可迁移点：用「真实案例池」代替主观热度判断，是选赛道的低成本方法。

**[R06 RefoundAI/lenny-skills](https://github.com/RefoundAI/lenny-skills)**：场景是「我到底缺哪块能力」说不清；决策是用可勾选技能项做自评；结果是缺口可定位到具体讲次。可迁移点：把模糊焦虑转成一张可勾选的表，就是本周工作坊的核心动作。

### 课堂讲解要点

结论前置：本讲是工作坊，讲师少讲、学员多写，下课必须交出一页纸；

| 环节 | 内容 | 板书 |
| --- | --- | --- |
| 导入 | 能力雷达自评 | 6 轴雷达 |
| 讲授 | 矩阵与画布用法 | 六格画布 |
| 演示 | 现场填一份样稿 | 样稿一页 |
| 练习 | 学员各自成稿 + 互评 | 证据物清单 |
| 总结 | 收一页纸 + 全章收束 | 一句话类比 |

生活类比：选赛道像选通勤路线——不是挑最热闹的那条街，而是挑从你现在的位置出发、换乘最少、最不容易迟到的那条。常见误区：追热门赛道却忽略迁移成本，结果 8 周里一半时间补基础，作品集来不及堆厚。

### 练习与讨论题

- 个人练习 1：填行业选择矩阵并写一句选择理由。参考要点：理由须同时提到岗位密度与迁移成本。
- 个人练习 2：完成个人定位画布，证据物至少挂 3 个 W1 讲次产出。参考要点：证据物具体可展示，不写「学了提示词」。
- 小组研讨：两人互评一页纸，指出「目标岗位与证据物是否对得上」。评分 rubric：指出 ≥1 处错配 2 分、给出改法 2 分、结论前置 1 分。

### 常见问题

1. **Q：能不能同时备两个赛道？** 可以，但要分主次：首选集中堆证据物，备选只做常识级了解，避免两头都浅。
2. **Q：迁移成本高是不是就别选？** 不是「别选」，是「别在第一份就选」；先在工作坊里把它列进 W7–W8 的纵深目标。
3. **Q：一页纸规划要写到多细？** 细到「第几周交哪件证据物、用什么验收标准」， vague 的规划等于没规划。

### 本讲术语

| 术语 | 英文 / 缩写 | 释义 | 易混点 |
| --- | --- | --- | --- |
| 行业选择矩阵 | Industry Matrix | 赛道 × 岗位密度 × 迁移成本 | 不等于热度榜 |
| 个人定位画布 | Positioning Canvas | 六格自定位工具 | 不等于简历 |
| 迁移成本 | Switching Cost | 补到可投所需投入 | 不等于学习投入 |
| 岗位密度 | Job Density | 目标城市可投岗位集中度 | 需按招聘信息校准 |
| 北极星指标 | North Star Metric | 最能代表长期价值的唯一指标 | 不等于日活 |
