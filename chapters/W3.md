## 0.4 本章核心概念

| 概念 | 一句话定义 | 易混淆点 |
| --- | --- | --- |
| Agent | 能自主规划并调工具达成目标的系统 | 区别在能否自己决定下一步 |
| ReAct | 推理与行动交替、观察后继续的循环 | 与链式调用不同 |
| 工作流 | 人预先画死的固定步骤图 | 分界是谁决定下一步 |
| 自主度等级 | L0 固定流程到 L3 自主规划的刻度 | 等级高不等于先进 |
| 工具契约 | 输入、输出、失败、权限四要素约定 | 重点在失败与权限 |
| 中断恢复 | 断点保存状态、可续跑或回滚 | 不等于报错重试 |
| RAG | 先检索证据再据证据生成 | 不等于把资料丢给模型 |
| 切片与重排 | 切块与对召回结果精排 | 找得到与排得准不同 |
| 引用溯源 | 答案标注可回查的原文位置 | 不等于附个链接 |
| GraphRAG / Agentic RAG | 图谱答全局、Agent 自主定检索策略 | 是补位而非替代 |
| 多模态 | 输入输出含图、音、文档等非纯文本 | 不等于多模型拼接 |
| 里程碑 ② | W3D5 评审通过后进入 W4 写 PRD | 不是里程碑 ⑤ 路演 |

## 0.5 本章关键方法框架
【补充】三个可复用模板。

框架一：自主度分级决策
1. 列出全部步骤与分支。
2. 评估每步失败代价（可忽略 / 可补偿 / 不可逆）。
3. 评估路径是否可穷举。
4. 定级：代价高且可穷举→L0；代价低且可穷举→L1；部分需判断→L2；不可穷举且允许试错→L3。
5. 为 L2、L3 补确认点、步数上限与日志。

框架二：RAG 九步链路检查表
接入 → 解析 → 切片 → 向量化 → 召回 → 重排 → 生成 → 引用溯源 → 评测；每步填「负责人 / 失败信号 / 兜底动作」，缺一列即未闭环。

框架三：里程碑 ② 七件套
① 流程图 ② 页面流 ③ 提示词与上下文设计 ④ 工具清单 ⑤ 异常兜底 ⑥ 评测样例 ⑦ 成本估算；每项写清「给谁看 / 验收口径」。

## 0.6 本章典型项目案例
案例一：[R15 langgenius/dify](https://github.com/langgenius/dify)。场景：算法人力有限却要做出客服问答演示。决策：用可视化编排把「检索 → 生成 → 拦截」画成固定节点图，自主度压在 L1。结果（定性）：产品与设计都能改流程。可借鉴的产品决策：自主度让位于可控性。

案例二：[R19 infiniflow/ragflow](https://github.com/infiniflow/ragflow)。场景：文档格式杂、答案需指回原文。决策：解析与切片可配置，强制保留引用溯源。结果（定性）：无答案时明确回「知识库未覆盖」。可借鉴的产品决策：护城河在解析质量与溯源可信。

案例三：[R40 shaxiu/XianyuAutoAgent](https://github.com/shaxiu/XianyuAutoAgent)。场景：电商客服议价。决策：多 Agent 协同，议价动作设人工约束。结果（定性）：自主被约束在边界内。可借鉴的产品决策：越贴近钱与承诺，越往 L0、L1 收。

## 0.9 本章常见问题（FAQ）
1. Q：Agent 和工作流选哪个？A：路径能画死就用工作流，否则上 Agent，多数业务停在 L1。
2. Q：自主度越高越好吗？A：不是，由失败代价决定，涉及钱与不可逆操作往 L0、L1 收。
3. Q：RAG 能彻底解决幻觉吗？A：不能，它只把「凭空编」变成「有据可查 + 可拒答」。
4. Q：切片越细越好吗？A：不是，太细丢上下文、太粗塞不进窗口，靠评测集调。
5. Q：GraphRAG 会取代向量检索吗？A：不会，它补的是跨文档全局归纳。
6. Q：多模态换模型就行吗？A：不是，产品工作在输入校验、复核、成本与可访问性。
7. Q：置信度阈值定多少？A：无通用值，课堂可设 0.7 作【教学假设】起点，须用评测集校准。
8. Q：日志是工程的事吗？A：不是，AI PM 要定义记哪些字段、谁能看、留多久。

## W3D1 周一 · Agent 架构原理

### 学习目标
1. 说出 Agent 四大件职责，各举 1 个产品侧例子。
2. 画出 ReAct 循环 6 个编号步骤，标出「观察」回到「推理」的回路。
3. 判断场景该选 L0–L3 哪级自主度，写出可控性、成本、失败代价三项理由。

### 核心概念
结论前置：Agent 与固定工作流的唯一分界是「谁决定下一步」——人画死步骤是工作流，模型临场决定是 Agent。四大件是最小结构，缺一件只算带工具调用的聊天。

四大件表（组件 / 职责 / AI PM 要拍板的事 / 生活类比）：

| 组件 | 职责 | AI PM 要拍板的事 | 生活类比 |
| --- | --- | --- | --- |
| 规划 Planning | 把目标拆成步骤 | 拆几层、能否改目标 | 厨师定顺序 |
| 记忆 Memory | 保留跨轮次上下文 | 记什么、记多久、谁清除 | 记住客人忌口 |
| 工具 Tool | 调外部能力取数或执行 | 能调哪些、权限多大 | 冰箱灶台 |
| 反思 Reflection | 检查结果决定是否重试 | 重试几次、何时转人工 | 尝一口补盐 |

Agent 与工作流对比表：

| 维度 | 固定工作流 | Agent |
| --- | --- | --- |
| 下一步由谁定 | 人 | 模型自主选 |
| 路径 | 可穷举 | 不可穷举 |
| 可控性 | 高 | 随自主度下降 |
| 成本 | 可预估 | 步数不定，须设上限 |
| 典型失败 | 分支没覆盖 | 空转、越权调用 |

结论：流程能画死就别放权，放权必须配日志与人工确认点。

### 方法框架
结论前置：本讲给出两套可直接套用的模板——ReAct 编号循环与自主度决策表。

框架 A：ReAct 循环 6 步：
1. 接收目标与上下文：明确要达成什么、有哪些约束。
2. 推理 Reason：判断离目标还差什么，定「下一步做什么」。
3. 行动 Act：按工具契约调一个工具，或提问补信息。
4. 观察 Observe：读取返回或回答，写入记忆。
5. 反思 Reflect：判断是否推进，未推进则记原因并决定是否重试。
6. 终止或回到第 2 步：达成目标、达步数上限、触发确认点时停止。

产品护栏：第 6 步须设最大步数与单步超时（【教学假设】如 8 步、10 秒），上线前按评测集标定；这两项是 AI PM 交付物。

框架 B：自主度等级产品决策表：

| 等级 | 定义 | 谁决定下一步 | 可控性 | 成本 | 失败代价适用 | 典型场景 |
| --- | --- | --- | --- | --- | --- | --- |
| L0 | 固定流程 | 人 | 最高 | 最低可预估 | 不可逆、涉及钱与承诺 | 报销审批、合同人工签发 |
| L1 | 固定流程 + 模型填槽 | 人画骨架 | 高 | 低 | 可补偿 | 客服问答、表单抽取 |
| L2 | 有限自主 + 确认点 | 模型选分支，关键动作暂停 | 中 | 中，需日志 | 中等、可回滚 | 数据分析、议价初稿 |
| L3 | 自主规划 | 模型全程决定 | 低 | 高且步数不定 | 低、允许试错 | 探索式调研、沙箱实验 |

结论：等级由「失败代价 × 路径可穷举性」决定，L3 只适用于错了也没关系且有人兜底的场景。

模板——自主度定级卡：场景 / 代价分级 / 路径可穷举性 / 等级 / 确认点 / 步数上限 / 定级人。

### 案例拆解
案例一：[R16 langchain-ai/langgraph](https://github.com/langchain-ai/langgraph)。场景：多步任务中途失败需回节点重跑。决策：用有状态、可回滚的图保存每步状态。结果（定性）：评审可指着节点说「失败就回这里」。可迁移点：可控性靠状态显式化。

案例二：[R17 xindoo/agentic-design-patterns](https://github.com/xindoo/agentic-design-patterns)。场景：团队想复用成熟套路。决策：把常见结构整理为模式（规划、路由、反思、多智能体）按场景选型。结果（定性）：评审从「能不能做」变成「用哪个模式、代价是什么」。可迁移点：模式化让 AI PM 与工程有共同语言；[R18 bojieli/ai-agent-book](https://github.com/bojieli/ai-agent-book) 按章代码可作中文底本。

### 练习与讨论题
个人练习 1：把「自动生成周报」拆 5 步，标注代价并定级。要点：对外发送属不可逆，定 L0 加人工签发；抽取可定 L1；须明确到等级。
个人练习 2：画 ReAct 6 步回路并标最大循环步数。要点：回路闭合、有终止条件、上限标【教学假设】且需评测标定。
小组研讨 3：辩论「客服该不该上 L3」。rubric：三项维度全覆盖 3 分、有佐证 2 分、给出折中等级 2 分、结论明确 1 分，共 8 分。

### 常见问题
1. Q：四大件哪个最易漏？A：反思——多数原型只有规划与工具，没有自检与重试上限，一出错就空转。
2. Q：ReAct 会无限循环吗？A：会，产品必须设最大步数、单步超时与人工确认点，这三件是 AI PM 交付物。
3. Q：L3 最该追求吗？A：不是，L3 只适合失败代价低且允许试错的场景，生产系统里 L0、L1 是多数。

## W3D2 周二 · Agent 产品设计与工作流实操

### 学习目标
1. 写出工具契约四要素并填出一张契约卡。
2. 按 6 步实操流程搭出含人工确认点、可中断恢复的工作流。
3. 判断在哪三个位置必须写日志，并为每个失败给出兜底动作。

### 核心概念
结论前置：Agent 产品设计不是「让模型更聪明」，而是「把不确定性关进契约、状态与兜底里」。六要点按「先拆、再约、再记、再刹车」递进。

六要点表（要点 / 结论 / 交付物）：

| 要点 | 结论 | 交付物 |
| --- | --- | --- |
| 任务分解 | 拆成可独立失败的步骤 | 步骤清单 |
| 工具契约 | 写清输入、输出、失败、权限 | 契约卡 |
| 状态与中断恢复 | 每步存状态，可续跑或回滚 | 状态字段表 |
| 人工确认点 | 高代价动作前暂停 | 确认点清单 |
| 可观测与日志 | 记录谁何时调了什么 | 日志字段表 |
| 失败兜底 | 每个失败都有去向 | 兜底映射表 |

工具契约四要素表（要素 / 要写什么 / 反例）：

| 要素 | 要写什么 | 反例 |
| --- | --- | --- |
| 输入 | 字段名、类型、必填、取值范围 | 只写传一个 query |
| 输出 | 成功与空结果结构 | 只写返回 JSON |
| 失败 | 超时、限流、越权、无数据四类码 | 只写报错 |
| 权限 | 谁能调、能读哪些、能否写删 | 共用一把钥匙 |

结论：先有步骤才有约定，有约定才有状态，有状态才谈得上刹车。工具契约像插座与插头——接口、电压、保险丝、谁有权合闸，四样缺一就烧设备。

### 方法框架
结论前置：本讲给出「工作流画布字段表」与 6 步实操流程两套模板。【补充】为大纲「工作流实操」的展开模板。

工作流画布字段表：

| 字段 | 含义 | 填写要求 | 示例（【教学假设】） |
| --- | --- | --- | --- |
| 节点 ID | 唯一标识 | 全局不重复 | N03 |
| 节点类型 | 开始 / 模型 / 工具 / 判断 / 人工 / 结束 | 六选一 | 工具 |
| 输入映射 | 上游字段 | 写「来源节点.字段」 | N02.summary |
| 输出映射 | 产出给谁 | 写目标字段 | N04.draft |
| 工具契约 ID | 引用的契约卡编号 | 必填 | TC-02 |
| 成功出口 | 下一节点 | 单一 | N04 |
| 失败出口 | 兜底节点 | 必填，不得空 | N09 转人工 |
| 确认点 | 是否暂停待人 | 是 / 否 + 角色 | 是 / 业务主管 |
| 状态快照 | 是否存断点 | 是 / 否 | 是 |
| 日志级别 | 记录粒度 | 简要 / 详细 | 详细 |
| 超时与重试 | 上限值 | 标【教学假设】 | 10 秒 / 2 次 |

结论：这张表就是 AI PM 交给工程的需求；「失败出口不得空」最常被漏掉。

6 步实操流程：
1. 写目标与验收口径：说明「什么算做完」，列 1 条成功与 1 条失败样例。
2. 拆步骤画骨架：拆成 5–8 个节点，只连成功出口。
3. 为每个工具节点填契约卡：补齐四要素。
4. 补三条横向设计：高代价节点加确认点、全部节点加状态快照、失败出口连兜底；[R16 langchain-ai/langgraph](https://github.com/langchain-ai/langgraph) 的状态检查点正是「可续跑」的实现。
5. 配可观测：定义日志字段（时间戳、节点 ID、输入输出摘要、Token 用量、耗时、结果码），定留存与可见角色。
6. 用评测样例走一遍：跑通正常路径、超时、越权各 1 条，确认都有去向，再冻结画布进入里程碑 ②。

模板——契约卡：工具名 / 契约 ID / 输入 / 输出 / 失败四类 / 权限 / 负责人 / 版本号。

### 案例拆解
案例一：[R15 langgenius/dify](https://github.com/langgenius/dify)。场景：一下午做出「报名信息抽取 + 自动回复」演示。决策：用可视化画布承载节点、分支与失败出口，确认点做成显式节点。结果（定性）：评审讨论「确认点该不该前移」，而非翻代码。可迁移点：把「刹车」画进图里，最易被认可。

案例二：[R40 shaxiu/XianyuAutoAgent](https://github.com/shaxiu/XianyuAutoAgent)。场景：客服议价与承诺属高代价动作。决策：多专家协同加上下文感知，议价类输出保留人工约束。结果（定性）：上下文不丢、越界动作被拦住。可迁移点：越贴近交易，越要把确认点与兜底前置；[R37 datawhalechina/llm-universe](https://github.com/datawhalechina/llm-universe) 中文实战可照着搭最小链路，验证第 6 步样例。

课堂节奏：

| 环节 | 内容 |
| --- | --- |

### 常见问题
1. Q：工具契约工程写 API 文档就行？A：不是，AI PM 必须定义失败四类与权限，这两项决定兜底与合规边界。
2. Q：确认点越多越安全？A：不是，过多会把 L1 拖成人工流程，按失败代价布点即可。
3. Q：日志记详细有隐私风险吗？A：会，AI PM 要定义「摘要不记原文、可见角色、留存期限」，延续 W2 合规要求。

## W3D3 周三 · RAG 架构与知识库产品

### 学习目标
1. 画出 RAG 九步全链路，为每步写出 1 个失败信号。
2. 写出知识库产品 PRD 必备字段清单，判断无答案策略怎么写。
3. 判断向量检索、GraphRAG、Agentic RAG 各适用哪类问题。

### 核心概念
结论前置：RAG 的产品价值不是「让模型知道更多」，而是「让每个答案都能指回证据，且没证据时敢说不知道」。护城河在解析、切片、溯源与评测。

RAG 九步全链路表（步骤 / 做什么 / AI PM 拍板 / 失败信号）：

| 步骤 | 做什么 | AI PM 拍板 | 失败信号 |
| --- | --- | --- | --- |
| 1 接入 | 收拢来源与格式 | 允许哪些来源 | 来源缺失、格式不支持 |
| 2 解析 | 从 PDF、扫描件、表格抽结构 | 表格图片要不要 OCR | 乱码、表格错行 |
| 3 切片 | 按语义切片段 | 切片大小与重叠 | 答案被切断 |
| 4 向量化 | 转可检索表示 | 用哪套表示 | 更新后未同步 |
| 5 召回 | 粗筛候选 | 召回几条 | 相关片段没进候选 |
| 6 重排 | 精排顺序 | 重排阈值 | 最相关排后面 |
| 7 生成 | 据证据写答案 | 提示词与上下文拼装 | 脱离证据发挥 |
| 8 引用溯源 | 标注文档与片段位置 | 引用粒度、能否回查 | 有答案无出处 |
| 9 评测 | 测命中与忠实度 | 评测样例与合格线 | 只测能不能答 |

结论：第 2、3、8、9 步是产品护城河，第 5 至 7 步偏工程调参。

知识库产品功能边界表（功能 / 必须做 / 明确不做）：

| 功能 | 必须做 | 明确不做 |
| --- | --- | --- |
| 权限 | 按空间角色隔离，检索随权限过滤 | 不做绕过权限的全局检索 |
| 更新 | 增量更新并标更新时间 | 不承诺改了立即全量生效 |
| 版本 | 保留历史、可回滚、标所用版本 | 不承诺跨版本答案一致 |
| 命中率 | 用评测集给可复核口径 | 不拿单次演示当命中率 |
| 无答案策略 | 证据不足时拒答，给转人工与补录 | 不允许编一段看似合理的话 |

【补充】「无答案策略」大纲未单列，属知识库产品化必需补充设计。

### 方法框架
结论前置：本讲给出链路落地、检索对比、PRD 字段三套模板。

框架 A：RAG 链路落地 5 步：
1. 定来源清单与权限矩阵。
2. 挑 20–30 条【教学假设】评测样例，含「应有答案、应有出处、应拒答」三类。
3. 逐段调解析与切片，用「答案是否被切断」验收。
4. 定召回条数与重排阈值，跑评测集看命中。
5. 冻结「引用粒度 + 拒答文案 + 转人工入口」三件。

框架 B：三类检索对比表：

| 方案 | 擅长 | 不擅长 | 成本 | 适用场景 |
| --- | --- | --- | --- | --- |
| 向量检索 | 逐条事实、语义匹配 | 跨文档全局归纳 | 低 | 制度条款、产品手册查询 |
| GraphRAG | 全局问题、关系归纳 | 单条精确查证、频繁更新 | 高，需建图维护 | 年报综述、多文档主题梳理 |
| Agentic RAG | 多轮检索、跨库选路 | 简单一问一答 | 最高且步数不定 | 复杂调研、跨库取证 |

结论：三者是补位不是替代。默认从向量检索起步，出现「全局归纳」才上 GraphRAG，出现「检索策略需判断」才上 Agentic RAG。

框架 C：知识库产品 PRD 必备字段清单：

| # | 字段 | 验收口径 |
| --- | --- | --- |
| 1 | 来源与格式白名单 | 允许类型与大小上限（【教学假设】） |
| 2 | 权限矩阵 | 空间 / 角色 × 可读 / 可写 / 可管理 |
| 3 | 解析与切片配置 | 表格是否 OCR、切片大小与重叠 |
| 4 | 更新与版本策略 | 增量频率、版本标识、回滚入口 |
| 5 | 召回与重排参数 | 召回条数、重排阈值 |
| 6 | 引用溯源粒度 | 到文档 / 片段 / 页码 |
| 7 | 无答案策略 | 拒答文案 + 转人工 + 补录入动线 |
| 8 | 命中率口径与评测集 | 样例数量、合格线、复测周期 |
| 9 | 日志与可见角色 | 谁问了、命中哪条、是否拒答 |
| 10 | 成本口径 | Token 与存储估算（【教学假设】） |

### 案例拆解
案例一：[R19 infiniflow/ragflow](https://github.com/infiniflow/ragflow)。场景：文档格式杂、答案需点回原文。决策：解析与切片可配置，强制保留溯源。结果（定性）：无答案时明确回「知识库未覆盖」。可迁移点：解析质量与溯源可信决定口碑。

案例二：[R20 microsoft/graphrag](https://github.com/microsoft/graphrag)。场景：用户问「这批文档共几类问题」而非某条款。决策：用知识图谱做全局归纳，而非加大召回。结果（定性）：能给出跨文档结构化归纳。可迁移点：先识别问题类型再选方案；[R21 NirDiamant/RAG_Techniques](https://github.com/NirDiamant/RAG_Techniques) Notebook 可当演示素材，[R22 Mintplex-Labs/anything-llm](https://github.com/Mintplex-Labs/anything-llm) 拆解知识库边界，[R04 Meirtz/Awesome-Context-Engineering](https://github.com/Meirtz/Awesome-Context-Engineering) 补齐「证据如何拼进上下文」。

### 课堂讲解要点
课堂节奏：

| 环节 | 内容 |
| --- | --- |
| 导入 | 开卷考试类比：为何更要标出处 |
| 讲授 | 九步链路、功能边界、三类检索 |
| 演示 | 同一问题用逐条查找与全局归纳各问一遍 |

| 总结 | 收口到「有据可查 + 敢说不知道」 |

板书：横向画九步链路，在第 8、9 步画圈。
生活类比：RAG 是「开卷考试」——翻目录找页码（召回）、划重点（重排）、写清引用哪页（溯源）、翻不到就写「资料未覆盖」（无答案策略）、考完用标准答案核对（评测）。

### 练习与讨论题
个人练习 1：为「差旅制度问答」写 3 条评测样例，含 1 条应拒答。要点：含应有出处、有应拒答、不编造条款，共 3 分。
个人练习 2：填 PRD 清单中「权限矩阵」与「无答案策略」。要点：权限随检索过滤、拒答带转人工与补录，共 4 分。

### 常见问题
1. Q：命中率低先调什么？A：先查解析与切片，再看召回条数，最后才动模型——多数「答不准」是证据没进来。
2. Q：知识库要做版本吗？A：要，答案必须标所用版本，否则制度更新后旧答案成合规风险。
3. Q：GraphRAG 该默认上吗？A：不是，建图维护成本高，只有全局归纳类问题才值得。

| 术语 | 英文/缩写 | 释义 | 易混点 |
| --- | --- | --- | --- |
| 检索增强生成 | RAG | 先检索证据再据证据生成 | 不等于微调 |
| 切片 | Chunking | 切成语义完整片段 | 不等于按字数硬切 |
| 召回 / 重排 | Retrieval / Rerank | 粗筛 / 精排 | 找得到与排得准不同 |
| 引用溯源 | Citation / Grounding | 标注可回查出处 | 不等于附网址 |
| 无答案策略 | Abstention | 证据不足时明确拒答 | 不等于换个说法再答 |

### 参考资料
- [R19 infiniflow/ragflow](https://github.com/infiniflow/ragflow)：看解析、切片、召回评测，解决「九步链路怎么验」。
- [R20 microsoft/graphrag](https://github.com/microsoft/graphrag)：看全局归纳设计，解决「何时不该只靠向量检索」。
- [R21 NirDiamant/RAG_Techniques](https://github.com/NirDiamant/RAG_Techniques)：看逐项 Notebook，解决「课堂演示与作业素材」。

### 本讲收尾
做 RAG 像带学生开卷考试：重点从来不是让他背下整本书，而是教会他翻到对的那一页、写清引用，翻不到就坦白说不知道。

## W3D4 周四 · 多模态产品设计

### 学习目标
1. 列出多模态输入侧与输出侧各 3 项设计要点。
2. 写出能力边界、延迟与成本、置信度与人工复核、可访问性四项清单。
3. 判断拍图识题、语音客服、文档审阅各自的主风险与兜底。

### 核心概念
结论前置：多模态产品的难点不在「能不能识别」，而在「识别不准时产品怎么收场」。本讲只谈产品侧设计，不给任何模型跑分、准确率数字或能力排行——模型能力对比属 W2 选型范围。

输入侧与输出侧设计表（侧 / 要点 / 产品动作）：

| 侧 | 要点 | 产品动作 |
| --- | --- | --- |
| 输入侧 | 格式与大小校验 | 列出支持类型与上限（【教学假设】） |
| 输入侧 | 质量预检 | 模糊、遮挡、静音时提示重传，别硬解 |
| 输入侧 | 隐私与授权 | 告知用途、留存期限与可见角色 |
| 输出侧 | 呈现形态 | 文本 / 结构化字段 / 标注框 / 语音 |
| 输出侧 | 置信度呈现 | 低置信标「需复核」，不伪装确定结论 |
| 输出侧 | 可回查 | 指回原图、原音、原页位置 |

四项设计清单表（维度 / 结论 / 产品要写的）：

| 维度 | 结论 | 产品要写的 |
| --- | --- | --- |
| 能力边界 | 明确「不做什么」更重要 | 不支持清单与降级路径 |
| 延迟与成本 | 链路更长，须给用户预期 | 延迟目标、成本口径（【教学假设】） |
| 置信度与人工复核 | 低置信强制转人工 | 阈值、复核队列、复核人角色 |
| 可访问性 | 视障听障用户不能被排除 | 替代文本、字幕、键盘可达、对比度 |

【补充】可访问性口径参考 W3C《Web 内容无障碍指南（WCAG）2.2》，属大纲未展开的产品补充要求。

结论：先管住「进来什么」，再管住「出去什么」，最后用四项清单兜住链路。

### 方法框架
结论前置：本讲给出场景设计 5 步与三场景拆解表。

框架 A：多模态场景设计 5 步：
1. 定输入清单：模态、格式、质量下限。
2. 定输出形态与置信度呈现方式。
3. 划能力边界：写明不支持清单。
4. 设人工复核点：阈值 + 队列 + 角色。
5. 补可访问性与降级路径，再写评测样例。

框架 B：三场景拆解表：

| 场景 | 输入 → 输出 | 主风险 | 置信度与复核 | 兜底 |
| --- | --- | --- | --- | --- |
| 拍图识题 | 题目照片 → 分步解析 + 标注框 | 模糊或手写体误识别，答案似对实错 | 低置信标「需核对题目」，不做终判 | 提示重拍 + 转人工答疑 |
| 语音客服 | 语音流 → 转写 + 意图 + 回复语音 | 口音噪声转写错，误触发高代价动作 | 意图置信低时先复述确认再执行 | 转文字渠道 / 人工坐席 |
| 文档审阅 | 扫描件或 PDF → 结构化字段 + 风险提示 + 原文定位 | 表格错行、印章漏检，漏报比误报更贵 | 关键字段强制复核，输出指回原页 | 标注「未识别项」交人工补录 |

结论：三个场景共同点是漏报与误判代价高，都不做全自动终判，一律保留人工复核与原文定位。

模板——多模态需求卡：模态 / 质量下限 / 输出形态 / 不支持清单 / 置信阈值（【教学假设】）/ 复核角色 / 可访问性 / 降级路径。

### 案例拆解
案例一：[R23 huggingface/transformers](https://github.com/huggingface/transformers)。场景：团队想同时支持文本、图像、音频输入，担心各接一套导致维护失控。决策：以统一的模型与处理接口组织多模态能力，产品侧只暴露「输入模态 + 输出形态」。结果（定性）：AI PM 在 PRD 里描述「用户传什么、系统回什么」，不绑定具体模型名。可迁移点：产品设计与模型实现解耦；本案例为技术参照，只写可验收的输入输出契约，不涉及模型评测分数或排名，也不编造企业数据。

### 课堂讲解要点
课堂节奏：

| 环节 | 内容 |
| --- | --- |
| 导入 | 医院看病类比：三种输入，疑难要会诊 |
| 讲授 | 输入输出侧、四项清单、三场景表 |
| 演示 | 故意传模糊图，走「预检 → 重传 → 复核」 |
| 练习 | 为语音客服写多模态需求卡 |
| 总结 | 收口：不准则收场，而非硬答 |

板书：中间画「输入 → 模型 → 输出」，两侧各挂「预检」与「复核」闸门。
生活类比：多模态像医院门诊——病人带来片子（图像）、口述症状（语音）、旧病历（文档），医生先判断资料清不清楚（预检），拿不准请专家会诊（复核），最后给视障听障患者能读能听的报告（可访问性）。

### 练习与讨论题
个人练习 1：为「拍图识题」写输入质量下限与 3 条不支持清单。要点：质量可判定、不支持项具体、每条有降级路径，共 3 分。
个人练习 2：给语音客服设置信度阈值并写低置信动线。要点：阈值标【教学假设】且需评测标定、先复述确认再执行、有转人工，共 4 分。
小组研讨 3：讨论「文档审阅里漏报与误报哪个更该优先防」。rubric：结论明确 2 分、说明代价 2 分、复核落在关键字段 2 分、有原文定位 2 分，共 8 分。

### 常见问题
1. Q：多模态把图音转文字再走文本链路就行？A：多数场景可以，但会丢位置、语气、版式信息，文档审阅与标注类须先保留原文定位。
2. Q：置信度阈值能抄通用值吗？A：不能，须用自己场景的评测样例回标；课堂示例值一律标【教学假设】。
3. Q：可访问性能上线后再补吗？A：不是，字幕、替代文本、键盘可达属输入输出设计，后补成本最高。

### 本讲术语

| 术语 | 英文/缩写 | 释义 | 易混点 |
| --- | --- | --- | --- |
| 多模态 | Multimodal | 输入输出含图、音、视频、文档 | 不等于多模型拼接 |
| 质量预检 | Input Validation | 识别前先判资料是否可用 | 不等于识别完再说 |
| 置信度 | Confidence | 系统对输出可靠程度的估计 | 不等于准确率 |
| 人工复核 | Human Review | 低置信输出转人判定 | 不等于事后抽检 |
| 可访问性 | Accessibility / a11y | 让视障听障用户也能使用 | 不等于界面美观 |

### 参考资料
- [R23 huggingface/transformers](https://github.com/huggingface/transformers)：看文本、视觉、音频、多模态模型的统一定义，解决「如何用统一语言描述能力」。
- [R15 langgenius/dify](https://github.com/langgenius/dify)：看应用侧承接上传与多步节点，解决「输入校验与降级路径怎么落进流程」。
- [R22 Mintplex-Labs/anything-llm](https://github.com/Mintplex-Labs/anything-llm)：看文档类产品呈现形态，解决「输出如何指回原文」。

做多模态就像门诊分诊：片子糊了先让病人重拍，拿不准就请专家会诊——负责任的医生从不硬着头皮下诊断。

## W3D5 周五 · 原型评审 I（里程碑 ②）

### 学习目标
1. 列出里程碑 ② 七件交付物，说出每件验收口径。
2. 用 100 分评分表给原型打分，指出至少 2 处扣分依据。
3. 用三段式话术回应 3 条驳回理由并给出补交物。

### 核心概念
结论前置：原型评审 I 不是「演示好不好看」，而是「这套设计能不能安全进入 PRD 阶段」的门禁。评审只问三件事——流程是否闭环、异常是否有去处、代价是否算得清。

里程碑 ② 定位表：

| 项 | 结论 |
| --- | --- |
| 里程碑 | ② 原型（W3D5），五个里程碑第 2 个 |
| 上游 | W2D5 ① 立项启动 |
| 下游 | W4D5 ③ PRD 评审大会 |
| 门禁含义 | 七件齐、评分达线，方可冻结为 PRD 输入 |
| 不评审什么 | 不评模型跑分、UI 视觉、商业经营数据 |

结论：任一项 0 分即整体不通过，不允许用高分抵消。

### 方法框架
结论前置：本讲给出交付物清单、100 分表、评审话术与驳回清单。【补充】评分分值与话术为教学补充模板。

框架 A：里程碑 ② 交付物清单（七件套）：

| # | 交付物 | 必须写清 | 验收口径 |
| --- | --- | --- | --- |
| 1 | 流程图 | 全节点含成功与失败出口、确认点 | 每个失败都有去向 |
| 2 | 页面流 | 用户从进入到完成的页面与状态 | 覆盖异常态与空态 |
| 3 | 提示词与上下文设计 | 系统提示、证据如何拼装 | 可复现、有版本 |
| 4 | 工具清单 | 契约 ID、权限、失败四类 | 与流程图节点一一对应 |
| 5 | 异常兜底 | 超时、越权、无数据、低置信 | 每条有文案与转人工路径 |
| 6 | 评测样例 | 成功、失败、应拒答三类 | 数量标【教学假设】、可复跑 |
| 7 | 成本估算 | Token、调用量、存储口径 | 假设标【教学假设】、有上限 |

框架 B：100 分评分表：

| 维度 | 分值 | 评分要点 |
| --- | --- | --- |
| 流程图与页面流 | 15 | 失败出口齐全 8、确认点合理 4、异常态与空态 3 |
| 提示词与上下文设计 | 15 | 可复现 6、有版本 4、证据拼装清晰 5 |
| 工具清单与契约 | 15 | 四要素齐全 8、权限最小化 4、与节点对应 3 |
| 异常兜底 | 15 | 四类全覆盖 8、文案不推责 4、转人工可达 3 |
| 评测样例 | 15 | 三类齐全 6、含应拒答 5、可复跑 4 |
| 成本估算 | 10 | 口径完整 5、假设标注 3、有上限 2 |
| 现场答辩 | 15 | 定级有理由 5、说清能力边界 5、直面最弱一环 5 |
| 合计 | 100 | 合格线【教学假设】70 分；任一项 0 分整体不通过 |

说明：评分权重属教学设计，数字均标【教学假设】，非企业数据。

框架 C：评审话术与常见驳回理由：
三段式话术：「我看到的（事实）→ 我担心的（风险）→ 我要的（补交物）」。结论前置，先说通过或不通过，再给依据，不给模糊收尾。

| 驳回理由 | 背后风险 | 补交物 |
| --- | --- | --- |
| 只有正常路径，没有异常兜底 | 线上一次超时就断链 | 四类兜底表 + 文案 |
| 用了 RAG 却没写无答案策略 | 证据不足时编造答案 | 应拒答样例 + 拒答文案 + 转人工 |
| 自主度选 L3 却没有确认点 | 高代价动作无人拦截 | 定级卡 + 确认点位置 + 步数上限 |
| 成本估算缺 Token 口径 | 上线后费用不可控 | 带【教学假设】的估算表 + 上限 |
| 评测样例只有 1 条 | 结论不可复跑 | 成功、失败、应拒答三类样例 |
| 流程图与工具清单对不上 | 工程无法照做 | 节点与契约 ID 对照表 |

### 案例拆解
案例一：[R15 langgenius/dify](https://github.com/langgenius/dify)。场景：要证明「流程闭环」而非口头描述。决策：以可视化画布作为流程图证据，节点即交付物。结果（定性）：评审逐节点核对失败出口，扣分有据。可迁移点：能被第三方核对的原型更易过评审。

案例二：[R19 infiniflow/ragflow](https://github.com/infiniflow/ragflow)。场景：评审质疑「答不准怎么办」。决策：把评测样例与引用溯源一并提交，主动展示应拒答样例。结果（定性）：最弱一环提前摆上台面，反而减少驳回。可迁移点：主动暴露弱项并给兜底，是答辩最稳策略。

### 课堂讲解要点
课堂节奏：

| 环节 | 内容 |
| --- | --- |
| 导入 | 房屋竣工验收类比：逐项打分 |
| 讲授 | 七件套、100 分表、三段式话术 |
| 演示 | 模拟答辩并当场打分 |
| 练习 | 互评原型，写 2 条扣分依据与补交物 |
| 总结 | 收口：过不了门禁就别进 PRD |

板书：左侧列七件套打勾，右侧写「扣分必附补交物」。
生活类比：原型评审像房屋竣工验收——不是看样板间拍得美不美，而是拿图纸逐项核对水电、消防、逃生通道，不合格就写进整改单，整改完才发钥匙。

### 练习与讨论题
个人练习 1：用 100 分表给给定原型打分，写 2 条扣分依据。要点：分值合计算对 2 分、依据对应评分要点 2 分、不给模糊评语 1 分，共 5 分。
个人练习 2：把一条驳回理由改写成三段式话术。要点：结论前置、含事实风险补交物三段、补交物可验收，共 3 分。
小组研讨 3：对一份「自主度 L3、无评测样例」的原型给出完整评审结论。rubric：结论明确 2 分、逐项打分 2 分、驳回准确 2 分、补交物齐全 2 分、话术符合三段式 1 分、指出最弱一环 1 分，共 10 分。

### 常见问题
1. Q：原型做到什么程度算够？A：七件套齐、失败出口全、评测样例能复跑即可，不需要真实用户量或漂亮视觉。
2. Q：评分没到合格线还能补吗？A：能，按驳回清单补交物后复评，这是门禁不是淘汰。
3. Q：答辩该不该藏弱点？A：不该，主动说出最弱一环并给兜底，比被当场问出来更稳。

### 本讲术语

| 术语 | 英文/缩写 | 释义 | 易混点 |
| --- | --- | --- | --- |
| 里程碑 | Milestone | 阶段门禁节点 | 不等于普通作业 |
| 原型评审 | Prototype Review | 冻结原型前的逐项打分 | 不等于演示走秀 |
| 交付物 | Deliverable | 可核对、可验收的材料 | 不等于讲过了 |
| 评分表 | Rubric | 维度 × 分值 × 评分要点 | 不等于主观印象分 |
| 驳回 | Rejection | 未达门禁需补交后复评 | 不等于项目失败 |

### 参考资料
- [R15 langgenius/dify](https://github.com/langgenius/dify)：看画布导出的流程结构，解决「流程图与页面流拿什么当证据」。
- [R19 infiniflow/ragflow](https://github.com/infiniflow/ragflow)：看评测与引用溯源，解决「评测样例与无答案策略怎么验收」。
- [R37 datawhalechina/llm-universe](https://github.com/datawhalechina/llm-universe)：看 MVP 搭建，解决「成本估算与最小可跑原型口径」。

### 本讲收尾
原型评审就像交房验收：图纸、水电、消防一项项对着查，不合格就写进整改单——拿了整改完的钥匙，才轮到下一章动笔写 PRD。

## 0.12 本章一句话收尾
给 Agent 配好工位就像给新助理办入职：先定他能自己拿多少主意，再给办事手册和权限卡，教他翻资料标出处、看不清就请人复核，最后把整套流程摆上验收台——手册齐、刹车灵，下一章才敢把 PRD 交到他手上。
