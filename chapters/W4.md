# 第 4 章｜W4 用户研究 · 需求分析 · AI 产品 PRD · 指标体系

> 本章只交付一个结论：把 W3 的「原型」变成一份**能评审、能开发、能验收、能度量**的 AI 产品 PRD，并在周五里程碑 ③ 通过评审。面向 UI 设计、软件测试等跨行业转岗学员，不要求写模型代码，只要求把「用户要什么、该不该上 AI、写得清、兜得住、量得出、评得过」六件事落成白纸黑字。它前接 W3 原型评审（里程碑 ②），后接 W5 的增长、A/B 实验与商业化——PRD 里的埋点与指标正是后续做实验、算成本的地基。全章按「认知 → 规格 → 兜底 → 度量 → 评审」递进。

## 0.1 本章学习目标

1. 说出 AI 用户研究相对传统调研的三点差异，写出含 10 条问题的访谈提纲。
2. 判断需求是否「必须上 AI」，用「AI 必要性判据」给出通过与不通过各一例。
3. 写出覆盖 12 章的 AI 产品 PRD 目录，逐章说明「写到什么颗粒度」。
4. 画出「异常—兜底—埋点」表，为超时、幻觉、越权等 7 类异常写降级策略。
5. 用 4 段 SQL 算出 DAU、次日留存、漏斗转化、按模型分组的成本/延迟，各写出「产品怎么读这个数」。
6. 完成一次 100 分评分表打分，列出里程碑 ③ 交付物与版本管理规则。

## 0.5 本章关键方法框架

> 【补充】以下三个框架为按讲次主题补入的可复用模板，编号步骤可直接套用于主项目。

**框架 A：需求四层 + AI 必要性判据（W4D1）**
1. 记原话：逐字记录，不改写。
2. 下沉四层：套模板「用户在【场景】要完成【任务】，被【痛点】卡住，做到【验收标准】即解决」。
3. 过判据卡：两问各写「是/否 + 理由」，皆过才立项。
4. 排优先级：按「价值 1–5 × 不可替代性 1–5 ÷ 失败代价 1–5」计分，高者进 P0；分值为教学评分设计。

**框架 B：PRD 十二章写作框架（W4D2）**
顺序：目标与非目标 → 用户与场景 → 流程 → 模型与提示词 / 上下文与知识库 → 评测集与验收线 → 异常与兜底 → 成本与性能 → 合规与隐私 → 埋点与指标 → 排期与依赖；模板见 W4D2 目录表。

**框架 C：指标树五步法（W4D4）**
1. 定北极星；2. 拆输入指标；3. 拆过程指标；4. 拆结果指标；5. 补护栏与 AI 五专有指标。模板：「北极星 → 四层 → 五专有 → 每段 SQL 的产物」。

## 0.9 本章常见问题（FAQ）

1. **结论：不是所有需求都该上 AI。** 用判据两问筛，不过就写「不做 AI」。
2. **结论：用户说不清是正常的。** 用行为追问代替「你想要什么」。
3. **结论：PRD 必须写非目标。** 不写边界，评审时范围会膨胀。
4. **结论：验收线要可判定。** 「评测集 100 条答对 ≥ 90 条」才合格（教学假设）。
5. **结论：兜底不等于报错。** 至少给出换模型/转规则/转人工之一。
6. **结论：先有事件再有指标。** 埋点没定，DAU、留存、漏斗都算不出。
7. **结论：看延迟要看 P95。** 平均值会掩盖长尾慢请求。
8. **结论：驳回不是否定，是修改清单。** 每条都要转成动作、责任人、版本号。

## W4D1 周一 · 用户研究与需求分析

### 学习目标

> 结论前置：AI 场景里用户往往「说不清想要什么」，研究的目的不是记录功能清单，而是还原他真正要完成的任务，并先判「该不该上 AI」。

1. 说出三点特殊性，并各举一例。
2. 写出含 10 条问题的访谈提纲，用「需求四层」整理成可验收条目。
3. 判断给定需求是否通过「AI 必要性判据」，用优先级矩阵排出 P0/P1/P2。

### 核心概念

**结论：难点不在「问得全」，而在「问得对」——用户给的是解法，你要的是任务。**

| 概念 | 一句话结论 | 易混淆点 |
| --- | --- | --- |
| 用户说不清需求 | 描述的是「他以为的解法」，不是任务 | 把「加个 AI 按钮」当需求 |
| 信任与预期管理 | 信任来自可预期，不是全能 | 承诺「什么都能答」反加速流失 |
| 失败容忍度差异 | 闲聊答错无感，账单、合同、医疗答错致命 | 按模型定容忍度 |
| Jobs-to-be-Done | 用户「雇」产品完成的那件事 | 与用户画像混淆 |
| 需求四层 | 任务 → 场景 → 痛点 → 验收标准 | 缺验收标准无法进评审 |

三点差异：① **说不清**——没见过 AI 能做什么，用行为追问还原；② **信任与预期**——演示惊艳、真实出错，访谈要问「能接受它错几次」；③ **失败容忍度差异**——出错代价直接决定 D3 兜底强度与 D4 护栏指标。

### 方法框架

> 【补充】以下判据、提纲模板与矩阵为按 W4D1 主题补入的教学内容，不改变讲次标题。

**框架 1｜三特殊性与访谈应对**

| 特殊性 | 典型表现 | 访谈应对 |
| --- | --- | --- |
| 说不清需求 | 「想要个智能点的东西」 | 问上次怎么做的、卡在哪一步 |
| 信任与预期 | 「应该啥都能答吧」 | 给失败样例，问能接受几次错 |
| 失败容忍度差异 | 闲聊随便、合同较真 | 问「答错一次会怎样、谁来背」 |

**框架 2｜访谈提纲模板与 10 条问题示例**
模板六段：① 暖场背景（不谈产品）→ ② 最近一次真实任务复盘 → ③ 卡点与绕过办法 → ④ 失败代价与信任边界 → ⑤ 给出错样例校准预期 → ⑥ 验收标准共创。10 条示例：
1. 上一次遇到这件事，是什么时间、什么场合？
2. 当时想完成什么？最后算「办成了」的标准是什么？
3. 现在没有这个产品时，你怎么解决？用了哪些工具或找了谁？
4. 最卡的地方是什么？卡住时一般怎么绕过去？
5. 如果答案给错了，最坏会怎样？谁来承担？
6. 这类事一周大概遇到几次？（教学假设采集，不引真实企业数据）
7. 十次里能接受它错几次？错了希望它怎么做？
8. 你希望它「直接给答案」还是「给草稿让你改」？为什么？
9. 如果它说「这个我不确定」，你会觉得可靠还是没用？
10. 下个版本只能解决一件事，你选哪件？怎么算解决？

**框架 3｜需求四层模板 + 判据卡 + 优先级矩阵**
四层模板：「用户在【场景】要完成【任务】，被【痛点】卡住，做到【验收标准】即解决」。判据卡两问：① 不用 AI 能否解决（能→「不必上 AI」）；② 用 AI 是否明显更优（否→「不值上 AI」）；两问皆过才立项。优先级矩阵：按「用户价值 1–5 × AI 不可替代性 1–5 ÷ 失败代价 1–5」计分，高者进 P0、居中进 P1、不过判据进 P2/不做；分值均为教学评分设计。

板书：左写「原话」，中写「四层」，右写「两问结论」，用箭头连成下沉链。生活类比：**装修前先问「你到底想在这个房间干什么」，而不是问「要不要买智能音箱」**——用户点名的是音箱，真正要的是「回家能松口气」。

### 练习与讨论题

| 个人 | 为主项目写 10 条访谈问题 | 覆盖六段 4 分、含失败代价与预期校准各 2 分、无诱导提问 2 分 |

### 常见问题

1. **结论：用户说不清，就问行为不问愿望。** 「上次怎么做的」比「你想要什么」可靠。
2. **结论：判据不过就不要硬上 AI。** 规则能解决的用规则，成本更低、验收更稳。
3. **结论：验收标准必须能判定。** 「更好用」不合格，要写成可数的条件。

## W4D2 周二 · AI 产品 PRD 写作

### 学习目标

> 结论前置：AI PRD 与传统 PRD 的差别不是「多写几页」，而是**必须写死不确定性**：模型、提示词、知识库、评测集、兜底、成本都要变成可验收条款。

1. 画出差异表，至少列出 6 项差异。
2. 写出完整 12 章目录，逐章说明「写什么、颗粒度、常见错误」。
3. 结合模板资源，写出主项目 PRD 前 3 章初稿。

### 核心概念

**结论：传统 PRD 描述「确定的功能」，AI PRD 描述「带概率的能力 + 出错时怎么办」。**

| 概念 | 一句话结论 | 易混淆点 |
| --- | --- | --- |
| 不确定性条款 | 把概率行为写成可验收边界 | 当成普通输入输出写 |
| 评测集与验收线 | 每个 AI 能力挂一组固定用例与通过线 | 与「上线后再看」混淆 |
| 提示词与上下文 | 是 PRD 一等章节，不是研发细节 | 塞进附录或不写 |
| 非目标 | 本版明确不做的能力边界 | 与「二期再说」混淆 |

### 方法框架

> 【补充】以下差异表与 12 章目录模板为按 W4D2 主题补入的教学内容。

**框架 1｜AI PRD 与传统 PRD 差异表**

| 维度 | 传统 PRD | AI 产品 PRD |
| --- | --- | --- |
| 输出确定性 | 输入相同则输出相同 | 同输入可能不同，需写容差 |
| 验收方式 | 功能点通过即完成 | 评测集达线才算完成 |
| 核心章节 | 流程、交互、字段 | 追加模型/提示词/上下文/知识库 |
| 失败描述 | 只写异常报错 | 必须写降级链路与告知话术 |
| 性能口径 | 响应时间 | 追加 P95 延迟与 Token 成本/次 |
| 合规范围 | 权限与隐私 | 追加内容安全、越权、幻觉风险 |
| 变更触发 | 需求变更 | 模型/提示词一改即需回归评测 |

**框架 2｜12 章 PRD 目录模板（写什么 / 颗粒度 / 常见错误）**

| 章节 | 写什么 | 写到什么颗粒度 | 常见错误 |
| --- | --- | --- | --- |
| 1 背景 | 用户问题与现状证据 | 引用访谈结论与四层编号 | 写行业趋势、不写证据 |
| 2 目标与非目标 | 本版要达成与明确不做 | 目标可量化，非目标逐条列 | 只写目标、漏非目标 |
| 3 用户与场景 | 角色、任务、触发时机 | 每场景一条「入口—动作—出口」 | 用画像代替场景 |
| 4 流程 | 主链路与分支 | 每步输入、输出、负责人 | 只画理想路径 |
| 5 模型与提示词 | 选型、提示词版本、参数 | 提示词原文入档并带版本号 | 只写「用大模型」 |
| 6 上下文与知识库 | 检索范围、切片、更新频率 | 字段级定义与召回口径 | 与模型章节混写 |
| 7 评测集与验收线 | 固定用例、评分标准、通过线 | 每条用例有期望输出与判定规则 | 写「回答更准」 |
| 8 异常与兜底 | 异常清单与降级路径 | 关联 D3 五列表 | 只写「提示错误」 |
| 9 成本与性能 | Token 成本/次、P95 延迟上限 | 给出上限值与超限动作 | 认为上线后才管 |
| 10 合规与隐私 | 数据留存、脱敏、内容安全 | 逐条对应自检清单 | 只写「符合法规」 |
| 11 埋点与指标 | 事件名、属性、口径 | 字段级定义，关联 D4 指标树 | 指标先于事件定义 |
| 12 排期与依赖 | 里程碑、外部依赖、风险 | 任务可验收、依赖有责任人 | 只写日期不写交付物 |

**框架 3｜写作顺序**：先 2（边界）→ 3（对象）→ 4（链路）→ 5/6（能力）→ 7（完成标准）→ 8/9/10/11（约束）→ 12（排期）；第 1 章最后补，避免用背景代替结论。

## W4D3 周三 · 方案设计与异常兜底

### 学习目标

> 结论前置：模型一定会出错，产品设计的价值是**让出错时不崩、不骗、可追溯**。

1. 列出至少 7 类异常，并说明各自触发条件。
2. 写出「异常—触发条件—用户可见表现—兜底策略—埋点」五列对照表。
3. 设计置信度分档展示与 4 条用户告知话术。

### 核心概念

**结论：兜底不是「报错」，是把用户从失败链路里接住并给一条能走的路。**

| 概念 | 一句话结论 | 易混淆点 |
| --- | --- | --- |
| 异常清单 | 先枚举模型、工具、权限的失败方式 | 只想到「超时」一种 |
| 降级策略 | 换模型 / 转规则 / 转人工三条备用路径 | 与「重试」混淆 |
| 置信度展示 | 分档提示，不做正确性承诺 | 把分数当准确率对外说 |
| 可追溯 | 每次兜底都要能被埋点回算 | 兜底了却没留痕 |

### 方法框架

> 【补充】以下异常清单、五列表、降级与话术模板为按 W4D3 主题补入的教学内容。

**框架 1｜异常清单（7 类）**：模型超时、模型拒答、幻觉（编造事实）、无答案（检索不到）、工具/接口调用失败、越权（访问不该看的数据）、重复调用（连点或循环）。

**框架 2｜异常—触发条件—用户可见表现—兜底策略—埋点对照表**

| 异常 | 触发条件 | 用户可见表现 | 兜底策略 | 埋点 |
| --- | --- | --- | --- | --- |
| 模型超时 | 单次调用超过 P95 上限（教学假设） | 一直转圈、无结果 | 重试一次，仍超时换备用模型，再转规则 | `model_timeout`、`fallback_type`、`latency_ms` |
| 模型拒答 | 触发安全或内容策略 | 得到「无法回答」 | 给边界说明 + 人工复核入口，不编答案 | `model_refusal`、`topic_tag` |
| 幻觉 | 含无来源事实、抽检不通过 | 看起来对但不可信 | 强制附引用；无来源则标「仅供参考」 | `is_hallucination`、`has_citation` |
| 无答案 | 召回为空或相似度低于阈值 | 答非所问或空白 | 明说「未找到依据」，给转人工入口 | `no_answer`、`retrieval_hit` |
| 工具失败 | 外部接口报错 | 功能半途中断 | 幂等重试 + 转规则，标「部分结果」 | `tool_error`、`retry_count` |
| 越权 | 命中非授权数据或角色 | 出现不该看的内容 | 立即拦截、返回无权限、记安全事件 | `permission_denied`、`risk_level` |
| 重复调用 | 同会话短时相同请求多次 | 重复扣费、答案刷屏 | 请求去重 + 结果复用 + 按钮置灰 | `duplicate_request`、`dedup_hit` |

**框架 3｜降级顺序与置信度展示**
降级顺序：① 可重试则幂等重试一次（限一次，防雪崩）；② 仍失败按「换模型 → 转规则 → 转人工」逐级下探；③ 每降一级都给可见表现与埋点。置信度分档（教学假设）：高（≥ 0.8）正常展示并附来源；中（0.5–0.8）附「建议核对」角标；低（< 0.5）不给结论，给「我不确定 + 转人工」。阈值须写入 PRD 第 7 章并纳入评测。**用户告知话术 4 条模板**（教学话术，非任何企业真实文案）：① 超时：「这次想得久了一点，我已换一条更快的路径，结果马上到」；② 无答案：「没有找到可靠依据，先不猜，你可以让我转给人工」；③ 疑似幻觉：「这条只能给到参考信息，已附出处，请核对后再用」；④ 越权：「这部分内容你暂无权限查看，已为你挡下并记录」。

### 案例拆解

| 引用 | 场景 → 决策 → 结果 → 可迁移点 |
| --- | --- |
| [R27 openai/openai-cookbook](https://github.com/openai/openai-cookbook) | 接口偶发超时导致整页空白 → 把超时、重试、备用路径写成工程范式并回填 PRD → 用户始终看得到一条可走的路 → **兜底策略要由工程范式校验** |

| 类型 | 题目 | 参考要点 / rubric |

### 常见问题

1. **结论：重试最多一次，且要幂等。** 无限重试会把小故障放大成雪崩。
2. **结论：置信度只做提示，不做承诺。** 低分档不给结论，直接转人工。
3. **结论：越权必须记录安全事件。** 可对照 [R12 OWASP/www-project-top-10-for-large-language-model-applications](https://github.com/OWASP/www-project-top-10-for-large-language-model-applications) 自检。

## W4D4 周四 · 数据指标体系与 SQL 实战

### 学习目标

> 结论前置：指标的作用不是「好看」，而是**让「这个 AI 产品值不值得继续做」变成一道能算的题**。

1. 画出「北极星 + 四层 + AI 五专有」指标树，说明每层回答什么问题。
2. 读懂 events 表字段定义，说明每个字段支撑哪个指标。
3. 写出 4 段 SQL，并逐段写出「产品怎么读这个数」。

### 核心概念

**结论：先定事件与口径，再写 SQL；SQL 只是把已经想清楚的问题算出来。**

| 层 | 回答什么问题 | 示例指标 |
| --- | --- | --- |
| 北极星指标 | 核心价值有没有长 | 每周成功解决的会话数（教学假设口径） |
| 输入指标 | 来了多少量 | 提问数、DAU |
| 过程指标 | 链路走不走得通 | 答案展示率、命中率 |
| 结果指标 | 价值达没达成 | 标记有用率、次日留存 |
| 护栏指标 | 有没有为增长牺牲底线 | 幻觉率、人工接管率、P95 延迟、Token 成本/次 |

AI 特有五指标（口径均为教学假设定义）：**命中率**（检索到可用依据的会话占比）、**幻觉率**（抽检判为编造的答案占比）、**人工接管率**（转人工会话占比）、**Token 成本/次**（单次调用平均推理花费）、**P95 延迟**（95% 请求在此耗时内完成）。易混点：命中率不等于答对率；幻觉率须靠抽检或评测集，不能由模型自报。

**框架 3｜4 段 SQL（每段含注释与「产品怎么读这个数」）**

```sql
-- SQL 1【教学假设】目标：按天统计日活跃用户数（DAU）
-- 口径：当天发起过 query_submit 的去重用户数
SELECT DATE(event_time)       AS dt,
       COUNT(DISTINCT user_id) AS dau
FROM events
WHERE event_name = 'query_submit'
GROUP BY DATE(event_time)
ORDER BY dt;
```
**产品怎么读这个数**：DAU 回答「有多少人真的来用」，看趋势不看单日；若 DAU 平稳但北极星（成功解决会话数）下滑，说明「人来了却没办成事」，应查过程指标而非拉新。

```sql
-- SQL 2【教学假设】目标：新用户次日留存（D1 Retention）
-- 口径：首次提问日为 cohort，次日仍发起 query_submit 记为留存
WITH first_day AS (
  SELECT user_id, MIN(DATE(event_time)) AS first_dt
  FROM events
  WHERE event_name = 'query_submit'
  GROUP BY user_id
),
next_day AS (
  SELECT DISTINCT f.user_id, f.first_dt
  FROM first_day f
  JOIN events e
    ON e.user_id = f.user_id
   AND e.event_name = 'query_submit'
   AND DATE(e.event_time) = DATE_ADD(f.first_dt, INTERVAL 1 DAY)
)
SELECT f.first_dt                                     AS cohort_dt,
       COUNT(DISTINCT f.user_id)                       AS new_users,
       COUNT(DISTINCT n.user_id)                       AS retained_d1,
       ROUND(COUNT(DISTINCT n.user_id) * 1.0
             / NULLIF(COUNT(DISTINCT f.user_id), 0), 3) AS d1_retention
FROM first_day f
LEFT JOIN next_day n
  ON n.user_id = f.user_id AND n.first_dt = f.first_dt
GROUP BY f.first_dt
ORDER BY f.first_dt;
```
**产品怎么读这个数**：次日留存回答「第一次用完还愿不愿意回来」。留存低常见根因不是功能少，而是首次就遇到幻觉或答非所问——要回看 D3 兜底与置信度分档，而不是先改界面。

```sql
-- SQL 3【教学假设】目标：主链路漏斗 提交问题 → 看到答案 → 标记有用
-- 口径：以 session_id 去重，逐步骤计数并算逐级转化率
SELECT
  COUNT(DISTINCT CASE WHEN event_name = 'query_submit'  THEN session_id END) AS step_submit,
  COUNT(DISTINCT CASE WHEN event_name = 'answer_shown'  THEN session_id END) AS step_shown,
  COUNT(DISTINCT CASE WHEN event_name = 'answer_useful' THEN session_id END) AS step_useful,
  ROUND(
    COUNT(DISTINCT CASE WHEN event_name='answer_shown' THEN session_id END) * 1.0
    / NULLIF(COUNT(DISTINCT CASE WHEN event_name='query_submit' THEN session_id END), 0)
  , 3) AS submit_to_shown,
  ROUND(
    COUNT(DISTINCT CASE WHEN event_name='answer_useful' THEN session_id END) * 1.0
    / NULLIF(COUNT(DISTINCT CASE WHEN event_name='answer_shown' THEN session_id END), 0)
  , 3) AS shown_to_useful
FROM events;
```
**产品怎么读这个数**：`submit_to_shown` 掉得多，多半是超时、拒答、无答案——查 D3 异常表；`shown_to_useful` 掉得多，说明答案给了但不靠谱——查幻觉率与评测集。用 `NULLIF` 防除零，让报表在空数据日也不报错。

```sql
-- SQL 4【教学假设】目标：按模型分组对比成本、P95 延迟、幻觉率、人工接管率
-- 口径：仅统计 is_ai_answer = 1；P95 用窗口函数按延迟排序取 95% 位置
WITH ranked AS (
  SELECT model_id, latency_ms, cost_rmb, is_hallucination, is_handoff,
         ROW_NUMBER() OVER (PARTITION BY model_id ORDER BY latency_ms) AS rn,
         COUNT(*)     OVER (PARTITION BY model_id)                      AS cnt
  FROM events
  WHERE is_ai_answer = 1
)
SELECT model_id,
       COUNT(*)                                                 AS calls,
       ROUND(AVG(cost_rmb), 4)                                   AS avg_cost_per_call,
       ROUND(AVG(latency_ms), 0)                                 AS avg_latency_ms,
       MAX(CASE WHEN rn <= CEIL(cnt * 0.95) THEN latency_ms END) AS p95_latency_ms,
       ROUND(AVG(is_hallucination), 3)                            AS hallucination_rate,
       ROUND(AVG(is_handoff), 3)                                  AS handoff_rate
FROM ranked
GROUP BY model_id
ORDER BY avg_cost_per_call;
```
**产品怎么读这个数**：这是「换不换模型」的决策依据——便宜但 P95 延迟高、幻觉率高的模型未必真省；护栏指标任一超线，就按 D3 顺序把流量切走。`MAX(CASE WHEN rn <= CEIL(cnt*0.95) ...)` 之所以是 P95，是因为 `rn` 已按延迟升序排好，取前 95% 里最大的延迟值即为分位点。

## W4D5 周五 · PRD 评审大会（里程碑 ③）

### 学习目标
