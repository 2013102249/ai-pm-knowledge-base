# 第 6 章｜W6 主项目实战：Vibe Coding 与 MVP 闭环

> 本章只交付一个结论：不会写代码的 AI 产品经理（AI PM），靠**规格驱动 AI 编码**就能把 MVP 从 PRD 推到可演示、可验收、可路演的闭环——核心动作是写清「要什么、怎么算做完了」，而不是自己写算法。本章是前五周的收口：W2 立项、W3 原型、W4 PRD、W5 中期评审的产出，在这一周变成可运行的东西。面向 UI 设计、软件测试等跨行业转岗学员，技术深度以「够用」为界。周五里程碑 ⑤ 直接为 W7 作品集供料。全章按「认知 → 冲刺 → 体验 → 验收 → 路演」递进。

## 0.5 本章关键方法框架

> 【补充】以下三个框架按讲次主题补入，编号步骤可直接套用。

**框架 A：规格先行六步工作流（W6D1）**
顺序：PRD → 任务清单 → 约束文件 → 让 AI 执行 → 验收 → 回归。每步收口动作是留下一份可复用的文字，不是口头确认。

**框架 B：MVP 闭环三层收敛（W6D2/D3）**
1. 范围层：只保一条主路径。2. 链路层：四段都可跑。3. 验收层：每段一条判据。

**框架 C：结业路演 8 段结构（W6D5）**
顺序：问题 → 用户 → 方案 → 演示 → 数据 → 决策与取舍 → 反思 → 下一步，每段一句结论 + 一个证据。

## 0.9 本章常见问题（FAQ）

1. **结论：不会写代码也能做 MVP。** PM 负责规格、验收与取舍，实现交给 AI。
2. **结论：Vibe Coding 更依赖 PRD。** 规格越模糊越容易被悄悄改需求。
3. **结论：AI 说「已完成」不算验收通过。** 须逐条对照标准判定。
4. **结论：做不完就砍功能，不砍闭环。** 只保一条主路径。
5. **结论：上下文不是越长越好。** 约束写进仓库约定比堆对话更稳。
6. **结论：功能测试与评测集回归互补。** 一个查通不通，一个查稳不稳。
7. **结论：5 人试用（教学假设）看「卡在哪」。** 行为观察比打分更定位问题。
8. **结论：没有企业数据就不编数据。** 用试用观察与过程记录做证据。

## W6D1 周一 · Vibe Coding 与 AI 工程提效

### 学习目标

> 结论前置：Vibe Coding 不是让 AI 随便写，而是 PM 写规格、AI 生成代码、PM 验收回归；本周产出都建立在这条分工上。

1. 说出 Vibe Coding 的定义与三条边界，写出「能 / 不能」清单。
2. 画出「规格先行」六步工作流，说明上下文与仓库约定的作用。
3. 写出三类翻车点的兜底动作，套用模板生成《项目约定文件》。

### 核心概念

> 结论前置：**PM 用规格驱动 AI 编码，而不是自己写算法。** 不必会写模型、调参、搭服务，但必须写清「要什么」和「怎么算做完」。

| 概念 | 一句话结论 | 展开 |
| --- | --- | --- |
| Vibe Coding | 自然语言即规格，AI 即执行者 | 验收权始终在 PM |
| 规格先行 | 先写完成定义再动手 | 顺序反了，AI 会用「能跑」代替「符合要求」 |
| 上下文 | AI 当前能看到的全部信息 | 缺失就靠猜 |
| 仓库约定 | 写进项目、始终生效的约束 | 给 AI 的岗位说明书 |
| 验收与回归 | 逐条判定 + 老用例复跑 | 验收看新任务，回归看老功能 |

> 【补充】能 / 不能清单（大纲未覆盖，按主题补入）。

| 能做什么 | 不能做什么 |
| --- | --- |
| 把明确规格转成代码骨架与页面 | 替 PM 决定做什么、为谁做 |
| 按任务清单一次一个任务实现 | 保证一次就对、不用返工 |
| 按约定补加载态、错误提示、注释 | 保证不悄悄改动需求、不替 PM 验收 |
| 生成修改与测试草稿 | 替代真实用户判断 |

工程边界只需理解「够用」：代理在「读上下文 → 规划 → 调工具 → 看结果」的循环里工作，**没写进上下文的常识它就可能自作主张**，见 [R36 Windy3f3f3f3f/how-claude-code-works](https://github.com/Windy3f3f3f3f/how-claude-code-works)；[R33 anthropics/claude-code](https://github.com/anthropics/claude-code) 说明约束应落在仓库里。

### 方法框架

> 【补充】以下六步工作流与《项目约定文件》模板按主题补入，可直接套用；方括号为填写位。

**规格先行六步工作流**

| 步骤 | PM 动作 | AI 动作 | 产出 | 卡点判据 |
| --- | --- | --- | --- | --- |
| 1 PRD | 复用 W4 PRD 圈定范围 | — | 范围与非目标 | 非目标是否写明 |
| 2 任务清单 | 拆成带验收标准的小任务 | — | 可验收任务列表 | 每条能否判定 |
| 3 约束文件 | 写约定、边界、禁止事项 | 读入约定 | 约定文件 | 是否放仓库根目录 |
| 4 AI 执行 | 一次只下发一个任务 | 生成/修改代码 | 可运行改动 | 是否超范围 |
| 5 验收 | 逐条对照标准判定 | 说明改了什么 | 通过/不通过清单 | 不写「大概可以」 |
| 6 回归 | 复跑老用例与主路径 | 修复回退问题 | 回归记录 | 老功能是否可用 |

**《项目约定文件》模板（可直接复制）**

```
【1】项目一句话
[谁，在什么场景，用本产品完成什么任务]

【2】本版范围与非目标
做：[一条主路径，逐段列出]
不做：[明确列出本版不实现的功能，防范围蔓延]

【3】技术边界
语言/框架、模型与调用方式：[填写]；不允许引入：[依赖/服务/付费项]

【4】目录与命名约定
[目录结构、命名规则]

【5】完成定义（每个任务必须满足）
- 功能按验收标准可判定、含加载态/错误提示/空状态
- 不改动任务范围外的文件、改动后主路径回归通过

【6】禁止事项
- 不自行增删需求、不改已确认的验收标准
- 不提交密钥与真实用户数据、不把「已完成」当验收结论

【7】验收方式
[PM 逐条判定；不通过写明原因并回到第 4 步]

【8】变更规则
[变更先改 PRD 与本文件，再下发任务；禁止口头改需求]
```

模板见 [R24 KhazP/vibe-coding-prompt-template](https://github.com/KhazP/vibe-coding-prompt-template)，起步见 [R05 liyupi/ai-guide](https://github.com/liyupi/ai-guide)。

> 【补充】三类翻车点与兜底动作。

| 翻车点 | 典型表现 | 兜底动作 |
| --- | --- | --- |
| 范围蔓延 | 顺手多做三个「顺便」功能 | 约定文件写死非目标；一次一任务 |
| 悄悄改需求 | 登录方式、字段口径被自作主张换掉 | 变更先改 PRD 与约定文件；逐条对照验收 |
| 无测试 | AI 说「已完成」就进下一任务 | 主路径冒烟 + 评测集回归，无记录不通过 |

| 讲授 | 定义、能/不能清单、六步工作流 | 只讲分工，不讲算法 |
| 演示 | 填约定文件并下发一个任务 | 边写边念完成定义 |
| 练习 | 各组套模板写约定文件 | 抓非目标与验收标准 |
| 总结 | 三类翻车点的兜底动作 | 收束到规格 + 验收 |

板书建议：左「规格（PM）」→ 中「执行（AI）」→ 右「验收/回归（PM）」，中间画红线。常见误区：当成不用写 PRD；相信「已完成」三个字。

生活类比：**装修房子**——你是屋主，不必会砌墙，但要把「几室几厅、插座位置、预算上限」写成清单交给施工队；清单写不清，返工的是你，拿尺子验收的也是你。

| --- | --- | --- |
| 个人 | 写「能 / 不能」清单，各 3 条 | 落到「AI 不替你定需求、不替你验收」 |
| 个人 | 把模板填成自己项目版本，≥ 5 个栏目 | 完成定义可判定、禁止事项具体 |
| 小组 | 情景：AI 悄悄改了登录方式，判断哪步失守 | 答「第 3 步约定文件 + 第 5/6 步验收与回归」 |

### 常见问题

1. **结论：Vibe Coding 更依赖 PRD。** 规格模糊时 AI 会用「看起来能跑」补空。
2. **结论：AI 说「已完成」不算验收通过。** 须逐条对照标准判定并写明结果。
3. **结论：上下文不是越长越好。** 约束固化进仓库约定更稳定、更省 Token。

## W6D2 周二 · 开发冲刺 I：核心链路

### 学习目标

> 结论前置：冲刺 I 只做一件事——让一条主路径从输入到结果真实跑通；功能做得多不算进度，主路径断了就是零。

1. 写出「最小闭环」一句话定义，画出主路径四段。
2. 写出任务拆解表（四列齐全，≥ 6 行，教学假设）。
3. 判断每日站会三问与版本回滚的触发条件。

### 核心概念

> 结论前置：**最小闭环 = 一条主路径跑通即可。** 先接通「输入 → 处理 → 输出 → 兜底」四段，其余功能进「以后再说」清单。

| 概念 | 一句话结论 | 易混点 |
| --- | --- | --- |
| 最小闭环 | 只保留一条可验证主路径 | 不是只做界面，后端到结果都要通 |
| 主路径 | 达成核心价值的最短路线 | 与功能列表混淆 |
| 任务拆解表 | 任务/验收标准/依赖/优先级四列 | 缺验收标准就无法判定 |
| 依赖 | 任务之间的先后关系 | 与「想先做哪个」混淆 |
| 优先级 | 按是否卡住主路径排序 | 与「哪个更好玩」混淆 |
| 版本与回滚 | 每步留可退回的存档 | 与重做一遍混淆 |

> 【补充】最小闭环三层收敛：范围层（砍到一条路径）→ 链路层（四段真实可跑）→ 验收层（每段一条通过判据）。三层缺一不算闭环。

### 方法框架

> 【补充】以下拆解表、站会节奏与回滚规则按主题补入，可直接套用；示例项目与行数为教学假设。

**任务拆解表模板（示例为教学假设）**

| 任务 | 验收标准（可判定） | 依赖 | 优先级 |
| --- | --- | --- | --- |
| 搭页面骨架 | 打开页面能看到输入框与结果区 | 无 | P0 |
| 接通模型调用 | 输入固定样例能返回非空结果 | 页面骨架 | P0 |
| 主路径贯通 | 输入 → 处理 → 结果展示全程无中断 | 模型调用 | P0 |
| 失败兜底 | 调用失败时显示可读提示且不白屏 | 主路径 | P0 |
| 结果可复制 | 一键复制，提示「已复制」 | 结果展示 | P1 |
| 冒烟脚本 | 一条命令跑通主路径并输出结果 | 全部 | P1 |

**每日站会节奏**

| 三问 | 要说清 | 产出 |
| --- | --- | --- |
| 昨天完成了什么 | 对照验收标准说通过/不通过 | 已通过任务清单 |
| 今天做什么 | 只报 1–2 个任务并说明依赖 | 当日任务清单 |
| 卡在哪 | 卡点是规格、依赖还是环境 | 待解卡点 + 责任人 |

**版本与回滚规则**

1. 一个任务一次提交，提交信息写任务编号与验收结论。2. 主路径跑通时打版本标签，作为可演示基线。3. 触发回滚：主路径中断、老用例回归不通过、约定文件被绕过。4. 回滚动作：退回上一个可用标签 → 记录原因 → 写回约定文件或任务清单 → 重新下发。

拆解方法参照 [R35 snarktank/ralph](https://github.com/snarktank/ralph)：**验收标准列必须先写**，否则「做完」没有判据；链路搭建参照 [R37 datawhalechina/llm-universe](https://github.com/datawhalechina/llm-universe) 的中文 MVP 实战与 [R15 langgenius/dify](https://github.com/langgenius/dify) 的可视化编排，先跑通再优化。

### 案例拆解

| 案例与引用 | 场景 → 决策 → 结果 → 可迁移点 |
| --- | --- |
| [R35 snarktank/ralph](https://github.com/snarktank/ralph) | PRD 很长无从下手 → 拆成逐条可验收条目驱动自主开发 → 每轮有可判定产出 → **先写验收标准，再排开发顺序** |
| [R15 langgenius/dify](https://github.com/langgenius/dify) | 零基础想尽快看到东西 → 用可视化编排先搭通「输入 → 编排 → 输出」 → 主路径当天可演示 → **先跑通再优化，别先造轮子** |

### 课堂讲解要点



| 环节 | 内容 | 讲师动作 |
| --- | --- | --- |
| 导入 | 展示「做了 8 个功能但主路径断了」的半成品 | 让学员判断算不算做完 |
| 讲授 | 最小闭环 + 三层收敛 + 拆解表 | 强调验收标准列 |
| 演示 | 把一条 PRD 拆成 6 行任务表 | 边写边问「怎么判定」 |
| 练习 | 各组填自己项目的拆解表 | 抓不可判定的验收标准 |
| 总结 | 站会三问与回滚触发条件 | 收束到留可退回存档 |

板书建议：横轴画「输入 → 处理 → 输出 → 兜底」四段，每段写一条判据；右侧列「以后再说」清单。常见误区：按兴趣排优先级；把「页面能打开」当闭环；不留版本标签。

生活类比：**搬家第一天**只求「床能睡、灯能亮、水能烧」——先把日子过起来，书柜怎么摆留到第二天；第一晚睡不了觉，装修再漂亮也没用。

### 练习与讨论题

| 类型 | 题目 | 参考答案要点 / 评分 rubric |
| --- | --- | --- |
| 个人 | 写最小闭环一句话定义并画四段主路径 | 含「一条主路径 + 可验证」；四段齐全；有通过判据 |
| 个人 | 填任务拆解表，四列齐全且 ≥ 6 行（教学假设） | 验收可判定、依赖顺序正确、P0 均卡主路径 |
| 小组 | 情景：站会有人说「昨天差不多做完了」。指出问题并改写 | 答「不可判定」；改写为「任务 X 按标准通过/不通过 + 证据」 |

### 常见问题

1. **结论：先做一条主路径，不做功能全集。** 一周只够把闭环跑通，其余进「以后再说」。
2. **结论：验收标准必须可判定。** 「能用」「差不多」不算标准，要写「输入 X 得到 Y」。
3. **结论：每个任务都要留可退回的存档。** 没有版本标签，出问题只能重做，回滚无从谈起。

## W6D3 周三 · 开发冲刺 II：功能与体验

### 学习目标

> 结论前置：AI 产品体验不是「把界面做漂亮」，而是「把不确定变成可预期」——用户随时知道系统在哪一步、出了错能怎么办。

1. 说出 7 类体验状态各自要解决的用户问题。
2. 写出《AI 产品体验检查清单》并逐项判定通过 / 不通过。
3. 判断「对输出不满意」应落到编辑、重试还是反馈入口。

### 核心概念

> 结论前置：**AI 会慢、会错、会没结果，三类不确定必须被产品层接住。** 规格不写清 7 类状态，AI 生成的代码默认只有「成功」一条路。

| 状态 | 用户在想什么 | PM 要写清的规格 | 不做的后果 |
| --- | --- | --- | --- |
| 加载态 | 它还在吗 | 加载文案、预计感、可取消 | 反复点击、以为死机 |
| 流式输出 | 写到哪了 | 逐块呈现、可停止、末尾收束 | 长时间白屏后被放弃 |
| 错误提示 | 出了什么事 | 发生了什么 + 能做什么 | 无从下手 |
| 重试 | 再试有用吗 | 区分可重试 / 不可重试 | 无脑重试浪费成本 |
| 编辑与反馈 | 我能改吗 | 可编辑输入、结果可复制、点赞点踩 | 只能重来一遍 |
| 空状态 | 是我没做对吗 | 说明原因 + 给下一步动作 | 空白页以为坏了 |
| 移动端适配 | 手机上还能用吗 | 布局、字号、热区、长结果折叠 | 小屏溢出、点不中 |

> 【补充】三条写法规则：① 错误提示同时写「发生了什么」和「能做什么」；② 重试区分可重试（超时、限流）与不可重试（输入不合法、权限不足）；③ 空状态必须给下一步动作，不留空白页。

### 方法框架

> 【补充】《AI 产品体验检查清单》按主题补入，可直接复制使用；勾选结果按自己项目逐项判定。

| # | 检查项 | 通过标准 | 常见遗漏 | 结果 |
| --- | --- | --- | --- | --- |
| 1 | 加载态文案 | 有明确进行中文案，非纯转圈 | 只有动画没文字 | ✓ / ✗ |
| 2 | 加载可取消 | 用户可中止本次请求 | 取消后仍后台扣费 | ✓ / ✗ |
| 3 | 流式呈现 | 结果逐块出现，可中途停止 | 全部生成才吐出 | ✓ / ✗ |
| 4 | 完成收束 | 有结束标记且可复制 | 不知是否写完 | ✓ / ✗ |
| 5 | 错误提示 | 含「发生了什么 + 能做什么」 | 只显示错误码 | ✓ / ✗ |
| 6 | 重试区分 | 可/不可重试分别给动作 | 一律「请重试」 | ✓ / ✗ |
| 7 | 编辑输入 | 不满意可改输入再发 | 只能清空重来 | ✓ / ✗ |
| 8 | 反馈入口 | 结果可复制、有点赞点踩 | 无反馈通道 | ✓ / ✗ |
| 9 | 空状态 | 说明原因并给下一步动作 | 一片空白 | ✓ / ✗ |
| 10 | 移动端布局 | 小屏不溢出、字号可读 | 桌面布局直接缩小 | ✓ / ✗ |
| 11 | 移动端操作 | 热区够大、长结果可折叠 | 点不中、滚不到底 | ✓ / ✗ |
| 12 | 一致性 | 7 类状态各页面口径一致 | 每页各写一套 | ✓ / ✗ |

用法：把清单作为「体验补位」任务的验收标准，逐行判定；任一 P0 项为 ✗ 则不进入 D4 验收。写法参照 [R15 langgenius/dify](https://github.com/langgenius/dify) 的运行过程可视化，以及 [R37 datawhalechina/llm-universe](https://github.com/datawhalechina/llm-universe) 中文教程里的异常处理示例。

| --- | --- |
| [R15 langgenius/dify](https://github.com/langgenius/dify) | 工作流运行久、用户不知在干嘛 → 把过程做成可视化节点与逐步输出 → 等待可预期、信任不流失 → **加载态与流式不是装饰，是信任机制** |
| [R37 datawhalechina/llm-universe](https://github.com/datawhalechina/llm-universe) | 新手搭 MVP 遇报错超时就卡住 → 示例里前置异常处理与提示 → 不被空白页挡住 → **错误态与空状态要写进规格** |

### 课堂讲解要点



| 环节 | 内容 | 讲师动作 |
| --- | --- | --- |
| 导入 | 展示「转圈 20 秒后白屏」的界面 | 让学员说出三个疑问 |
| 讲授 | 7 类状态表 + 三条写法规则 | 每类配一句用户独白 |
| 演示 | 下发一条体验规格并检查结果 | 强调「错了能做什么」 |
| 练习 | 各组用清单逐项判定自己项目 | 抓空状态与移动端 |
| 总结 | 清单作为 D4 验收输入 | 收束到不确定被接住 |

板书建议：画「发请求 → 等待 → 出结果」时间轴，在两处缺口贴 7 类状态。讲师提示：只写「用户看到什么、能做什么」。常见误区：只做成功态；错误提示只写「出错了」；忽略移动端。

生活类比：**点外卖**——「已接单 / 骑手取餐 / 还有 3 分钟」就是加载态与流式，「商家已打烊，换一家或稍后重试」就是错误提示与重试；最怕下单后一直转圈什么都不说。

| 类型 | 题目 | 参考答案要点 / 评分 rubric |
| --- | --- | --- |
| 个人 | 用清单逐项判定自己项目，列出全部 ✗ 项及改进动作 | 12 项全覆盖、每个 ✗ 有具体动作、不写「优化体验」 |
| 个人 | 为「模型超时」写一条错误提示文案 | 含两要素；区分可重试 |
| 小组 | 情景：用户对输出不满意。判断给编辑、重试还是反馈入口 | 答「先给编辑输入 + 反馈入口，超时类才给重试」；理由落到用户意图 |

### 常见问题

1. **结论：加载态和流式输出是必做项。** 它们解决「系统还在吗」的信任问题。
2. **结论：错误提示必须给用户一个动作。** 只写「出错了」等于把问题推回给用户。
3. **结论：移动端适配要写进规格。** 默认生成的代码常只照顾桌面，小屏溢出是常见漏项。

| 流式输出 | Streaming | 逐块返回结果 | 与性能优化混淆 |
| 加载态 | Loading State | 等待期间的可预期反馈 | 与纯动画混淆 |
| 空状态 | Empty State | 无结果时的引导界面 | 与空白页混淆 |

| 移动端适配 | Responsive / Mobile | 小屏布局、字号与热区 | 与缩小桌面版混淆 |

## W6D4 周四 · 测试验收与真实用户试用

### 学习目标

> 结论前置：验收回答「做没做完」，试用回答「能不能用」，两者都不能由 AI 自己说了算；结论必须由清单和真实用户给出。

1. 写出《验收清单》五类检查项，逐项给出通过判据。
2. 写出 5 人真实用户试用脚本（教学假设），含任务、观察点、访谈问题三件套。
3. 用反馈分级表把试用反馈排进修复优先级。

### 核心概念

> 结论前置：**验收 = 逐条判定 + 留下记录。** 「跑通了」只是主观感觉，可复跑的用例与可查的记录才是证据。

| 五类检查 | 查什么 | 通过判据 | 谁负责 |
| --- | --- | --- | --- |
| 功能测试 | 主路径与任务验收标准 | 逐条通过，无阻断项 | PM 判定 |
| 评测集回归 | 固定用例集输出质量 | 改动前后质量不回退 | PM 复跑（沿用 W2） |
| 异常与边界 | 空/超长/超时/断网/重复提交 | 不白屏、提示可读可行动 | PM 设计，AI 实现 |
| 安全与隐私 | 密钥、越权、日志脱敏 | 无密钥回显、测试数据用完即删 | PM 自检 |
| 性能与成本 | 首字返回时间、调用成本 | 落在约定阈值内（教学假设） | PM 记录 |

> 【补充】功能测试查「通不通」，评测集回归查「稳不稳」，两者互补；评测集与验收线沿用 W2 体系，本章只做落地复用，不重复讲原理。

### 方法框架

> 【补充】以下三份模板按主题补入，可直接复制；人数、条数、阈值均为教学假设。

**《验收清单》模板**

| 类别 | 检查项 | 通过判据 | 结果 |
| --- | --- | --- | --- |
| 功能测试 | 主路径按拆解表逐条复跑 | 每条标准通过 | ✓ / ✗ |
| 评测集回归 | 固定用例集（教学假设：≥ 20 条）复跑 | 质量不回退 | ✓ / ✗ |
| 异常与边界 | 空/超长/超时/断网/重复提交 5 类 | 不白屏、提示可行动 | ✓ / ✗ |
| 安全与隐私 | 密钥不回显、不越权、日志脱敏 | 逐项核对通过 | ✓ / ✗ |
| 性能与成本 | 首字返回时间、调用成本 | 在阈值内（教学假设） | ✓ / ✗ |

**《5 人真实用户试用脚本》模板（5 人）**

| 阶段 | 任务（不解释用法） | 观察点 | 访谈问题 | 记录 |
| --- | --- | --- | --- | --- |
| 开场 | 「请用产品完成一次【核心任务】」 | 找不找得到入口、有无犹豫 | 「你以为点这里会发生什么？」 | 原话速记 |
| 任务 1 | 走完主路径 | 哪步停顿最久、是否回退 | 「刚才哪一步最不确定？」 | 卡点 + 时间点 |
| 任务 2 | 故意给一次会出错的输入 | 是否看懂提示、找到重试 | 「提示告诉你该怎么办了吗？」 | 是否自助恢复 |
| 任务 3 | 换小屏或空输入再试 | 布局可读吗、空状态给下一步吗 | 「如果收费你还会用吗？」 | 意愿与理由 |
| 收尾 | 自由试用 | 自发行为、额外提问 | 「只能改一处，你改哪？」 | 一条最重要意见 |

访谈规则：不解释、不引导、不替用户操作。

**《反馈分级与修复优先级表》**

| 等级 | 判定 | 示例 | 处理动作 | 时限（教学假设） |
| --- | --- | --- | --- | --- |
| P0 | 阻断主路径或涉安全隐私 | 提交后白屏、密钥回显 | 立即修，复跑全部用例 | 当天 |
| P1 | 多数人卡住 | 错误提示看不懂 | 本版必改，改完回归 | 路演前 |
| P2 | 体验瑕疵，可绕过 | 移动端字号偏小 | 记入「以后再说」 | 下一版 |
| P3 | 愿望清单 | 「要能导出就更好了」 | 只记录，不进本版 | 不排期 |

3. **结论：5 人试用（教学假设）看「卡在哪」。** 行为观察比打分更定位问题。

## W6D5 周五 · 主项目结业路演（里程碑 ⑤）
